Scenarios:
(a) `adopt-order`: open two web tabs (A on /opener, B on /target); click the `_blank` link in A's page context; require one `adoptTab` push with `openerTabId==A` (the positive control every absence leg reuses: the recorder demonstrably sees adoptTab pushes in this session); require the new widget directly after A in the strip order; require shell-window count 1 (SHELL_READY sentinel) and no second top-level stock context; then trigger plain `window.open` from the page button and require the same adjacency; then close the adopted tab and require selection back on A (reselect leg — proves the decided Theia close-reselect, CONTEXT D-05b).
(b) `adopt-opener` (checker B4): in the adopted tab's page context read `window.opener` non-null, then run a `postMessage` round-trip adopted→opener→adopted and require both legs to complete.
(c) `adopt-popup` (checker B3): trigger `window.open(url, name, "width=400,height=300")` from the page button; require a NEW top-level stock window context with the URL (same dual-proxy instrument as gui01-window) and NO new web-tab widget for it.
(d) `adopt-focus`: middle-click-path adopt (background) leaves A's page focused; foreground `window.open` activates the new tab (read focus from chrome active element + pushed state).
(e) `adopt-fallback` (checker W5): suppress the frontend `adoptTab` subscription for one shot (drop the ack, keep the recorder); trigger `_blank`; wait on the stock-window BiDi context event (event-waited: subscribe, then require the context within the 5 s timer plus harness margin — never a fixed sleep longer than the timer); require the URL in that stock-window context and no adopted widget for the pcKey; the paired positive control is the adopt-order leg (same session, same recorder saw an adoptTab push open exactly one tab, so "no adopted widget" is a discriminating absence).
(f) `adopt-scheme`: click the `javascript:` link; require `refused-scheme` outcome surfaced (no new widget, no stock context, no navigation of A; positive control is the adopt-order leg in the same session).
(g) `adopt-unknown-key` (checker W4): ack a fabricated `pcKey` (`pc-999999`) and require the `unknown-tab` reply AND the orphan widget dropped (no widget with that tabId remains).
`--self-test`: clean control (all seven green) then one session per plant, each scored only on its scenario, requiring a FAIL line containing the expected text; a plant that did not apply fails the self-test. Plants: (1) `adopt-append-at-end` (adopt inserts at strip end) → expect `directly after`; (2) `reselect-opener-off` (close selects neighbour instead of opener) → expect `opener`; (3) `opener-null` (adopted page sees null opener) → expect `opener`; (4) `popup-becomes-tab` (popup features land as a tab) → expect `stock window`; (5) `background-activates` (background adopt activates) → expect `opener keeps focus`; (6) `fallback-off` (drop ack AND suppress fallback) → expect `stock window`; (7) `adopt-javascript` (adopt path loads javascript:) → expect `refused`; (8) `unknown-key-keeps-widget` (orphan widget survives unknown-tab) → expect `dropped`.
