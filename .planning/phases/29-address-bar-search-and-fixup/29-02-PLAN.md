<objective>
Prove development addresses open (BAR-02) and ship, in the same plan, the technical ruling that makes them safe: an overlay load to another loopback port never carries the Theia token cookie (REQUIREMENTS technical rulings 2026-10-20; CONTEXT locked decision 6). Then classify every store kind so the privileged kinds later plans add (Shift+Del, clipboard) are gated from their first commit.

Purpose: 29-01 made typed `host:port` and IP text routine through URI fixup. Loading `http://127.0.0.1:<port>` from a typed address already worked before this phase, so 29-01 widened nothing, but BAR-02's acceptance is the ruling plus the addresses, together.

Decided (autonomous, recommended): the strip is stricter than 29-RESEARCH Pattern 6. The token is kept only on requests to the sidecar's own port that come from the Theia frame, chrome (system principal) or a Theia-origin worker; every other request to `127.0.0.1` loses it. This covers overlays, the stock browser window and workers by the port alone, so it does not rest on assumption A3 (worker attribution). An overlay that loads the sidecar's own port also loses it (research: intended).

Decided (autonomous, recommended; tightens 29-RESEARCH Pattern 6, which installed from `webTabOpen`): the observer is installed when the sidecar port is registered (`PowerBrowserAPI.setGroupSenderPort`), not when the first web tab opens. A GUI-01 stock window can be opened before any web tab exists, and an install keyed on `webTabOpen` would leave it carrying the token to another loopback port. `setGroupSenderPort` runs in `TheiaService._swap`, which `_spawnAndGate` calls synchronously right after the cookie is minted, so the observer is live before any request in the process can carry the token.

Output: the strip in the search area, `scripts/verify-token-cookie-strip.mjs`, live scenarios `token-cookie` and `dev-addresses`, rule 12 in the bridge gate.
</objective>
