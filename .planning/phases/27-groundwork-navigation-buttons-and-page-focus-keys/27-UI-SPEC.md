# Phase 27 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note.** This phase extends the chrome bar contracted in 13-UI-SPEC (tokens, geometry,
type, colour, focus ring, motion all inherited, nothing re-specified unless it changes). It adds:
the single Reload/Stop element, the hard-reload gesture, the Back/Forward session-history menu,
the optional Home button and its two settings, shortcut text in every nav-button tooltip,
middle-click on Back/Forward/Reload, link drop on New Tab, and the page-focus key set
(NAV-01..06, KEY-01..05). The groundwork (push router, `webTabActivated`, widened push,
`webTab*` kinds, layer policy, `gBrowser` stand-in policy, privileged-kind rule, page-focus
context key, live-probe harness) has no visible surface of its own; it appears here only where it
fixes a visible behaviour (the layer policy, the page-focus context, focus hand-off).

Hard rules that bind every row below: never fork or patch Theia core (all UI is
`@powerbrowser/chrome-bar` composition); Firefox internals only through `PowerBrowserAPI.sys.mjs`;
no custom browser chrome beyond the chrome bar itself; no internal identifier in user-facing text;
the product name comes from the configured application name, never a literal.

Mode: `/gsd-autonomous` (Chris's standing nonstop instruction). Every choice not fixed upstream
is marked **Decided (autonomous, recommended)** and is consistent with the chrome-bar tokens
and the sketch findings.

## Copywriting Contract

Inherited rules: no internal identifier in user-facing text (no pref key, kind name, port, timeout,
raw exception); the product is named by the **configured application name** —
`FrontendApplicationConfigProvider.get().applicationName`, read at render time — never by a
literal. Chrome-bar source for this phase carries no brand literal and no literal fallback: if the
configured name is empty, the sentence starts with "The browser" instead. Naming stays
"chrome bar". Every error ends with a next step that is a real affordance on screen.

`{App}` below means the configured application name.

| Element | Copy |
|---------|------|
| Primary CTA | **"Reload"** / **"Stop"** — one button whose label is the action it performs now. |
| Back tooltip | **"Back (Alt+Left Arrow)"** |
| Forward tooltip | **"Forward (Alt+Right Arrow)"** |
| Reload tooltip | **"Reload (Ctrl+R)"** |
| Stop tooltip | **"Stop (Esc)"** |
| Home tooltip | **"Home (Alt+Home)"** |
| New Tab tooltip | **"New Tab (Ctrl+T)"** |
| Accessible names | `aria-label` stays verb-only: "Back", "Forward", "Reload" or "Stop", "Home", "New Tab". The shortcut goes in `aria-keyshortcuts` (Back `Alt+ArrowLeft`, Forward `Alt+ArrowRight`, Reload `Control+R F5`, Stop `Escape`, Home `Alt+Home`, New Tab `Control+T`). |
| History menu entry | The entry's page title; when the title is empty, its address; when both are empty, "Untitled page". Labels longer than 60 characters are cut to 57 characters plus "…". |
| History menu error (empty state) | One disabled item: **"{App} couldn't read this tab's history. Use Back and Forward to move one page at a time."** |
| Home-failure row | **"{App} can't open your home page. Press Enter to change it in Settings."** (one dropdown row, no footer hint; Enter or a click opens Settings filtered to the home-page setting) |
| Setting: show Home button | Description: **"Show the Home button next to Reload."** |
| Setting: home page | Description: **"The page the Home button and Alt+Home open, such as https://example.com. Leave it empty to open an empty page."** |
| Empty state | No new list surface besides the history menu (above). An empty home-page setting is not an error: Home opens the empty page and focuses the pill, exactly as New Tab does. |
| Destructive confirmation | **None.** Ctrl+W with the page focused closes the tab with no confirmation, as in Firefox and as the strip's close control already does; no other action in this phase removes data. |

Shortcut text source (Pitfall: tooltip shortcut text): every tooltip string is built from the
**same derived shortcut table** that `verify-shortcut-relay.mjs` guards, never from
`KeybindingRegistry` (which would show Theia's binding where the relay handles the Firefox key).
The strings above are the Linux and Windows rendering, which this phase ships and verifies; the
macOS rendering comes from the table's macOS column.

Settings keys (shown by Theia's Settings editor as "Browser › Show Home Button" and
"Browser › Home Page"): `browser.showHomeButton` (boolean, default `false`) and `browser.homePage`
(string, default `""`). **Decided (autonomous, recommended):** a brand-neutral `browser.` prefix,
so a rebranded build never shows this product's name in Settings; off by default because current
Firefox ships without a Home button in its default toolbar.

New copy lives inside the derived surface of `verify-shell-error-copy.mjs` /
`shell-error-copy-no-internals`; the planner confirms that check accepts the `{App}` substitution
rather than requiring a literal product name.

## Interaction Contract (NAV-01..06, KEY-01..05)

### Chrome bar composition (left to right)

Back, Forward, Reload/Stop, **Home (only while `browser.showHomeButton` is on)** | address pill |
New Tab | mode toggle. This is Firefox's order. Home is removed from layout when the setting is off
(not dimmed): it is a user choice, so its layout shift is expected; toggling the setting
updates the bar live, with no reload. With Home on, the narrow-window rule is unchanged: the pill
shrinks first, to its 120px minimum; buttons never wrap or clip.

Focal point: the address pill stays the bar's focal point. Home and the Stop state are 32×32
icon buttons in the existing nav cluster and add no colour, weight or size that competes with it.
The nav labels are single verbs (Back, Forward, Reload, Stop, Home) on purpose: that is Firefox's
wording, kept for parity, and the accessible name plus `aria-keyshortcuts` carries the rest.

### Reload / Stop (NAV-01, NAV-02)

- **One element.** The Reload button becomes Stop while the active web tab's pushed `loading` is
  true, and becomes Reload again when it is false. Only the glyph (`codicon-refresh` ↔
  `codicon-close`), the `aria-label`, `aria-keyshortcuts` and the tooltip change. The element is
  never re-mounted, so keyboard focus on it survives every load (Pitfall: wrong focus after a
  Stop/Reload swap). The glyph swaps with no animation.
- Stop is enabled whenever it shows. Reload keeps its existing enablement (`canReload`).
- Click on Stop stops the load. **Decided (autonomous, recommended), from Firefox:** after the
  button turns from Stop back into Reload it ignores clicks for 650 ms, so a double-click on Stop
  never reloads the page that just finished. It is not dimmed during that window.
- **Esc stops the load** while focus is inside the web page, on the reply path: a page that
  handles Esc itself keeps it, as in Firefox. In the pill, Esc keeps the 13-UI-SPEC sequence (first
  closes suggestions, second restores the committed address); a further Esc with nothing left to
  close or restore stops the load.
- **Hard reload:** Shift+click on Reload, and Ctrl+Shift+R or Ctrl+F5 with the page focused,
  reload without the cache. Hard reload has no distinct glyph or tooltip; the button looks the same
  whether Shift is held or not (Firefox parity).
- No progress bar and no spinner in the bar. The tab title's existing loading spinner stays the
  only progress indicator.

### Back / Forward session-history menu (NAV-03)

- **Triggers:** right-click; press-and-hold of the primary button for **500 ms** (Firefox's
  click-hold delay; the release after a hold does not navigate); and the keyboard context-menu key
  or Shift+F10 on a focused Back or Forward button (the same `contextmenu` event). A plain click
  still goes one step. The browser's own context menu never appears over these buttons.
- **Rendered as Theia's `.lm-Menu` through `ContextMenuRenderer`**, as `layout-controls-widget.tsx`
  does, anchored at the button's bottom-left corner. Stock `.lm-Menu` keyboard handling (arrows,
  Enter, Esc) and stock edge flipping apply; nothing in `.lm-Menu` is restyled.
- **Content:** Back and Forward open the same list (Firefox parity): up to **15** entries of the
  active tab's session history, a window centred on the current entry, **newest at the top**. The
  current entry carries the stock check mark and choosing it does nothing. Choosing any other entry
  goes to it (`webTabGotoIndex`). No favicons in this phase.
- The menu is only reachable from an enabled button, so it always has at least two entries.
- The history is read when the menu is requested; the menu opens when the reply arrives, with no
  spinner. A failed read opens the menu with the single disabled error item from the Copywriting
  Contract.
- **Layer policy, rule (a):** `.lm-Menu` is in `BLOCKING_LAYER_SELECTOR`, so the page is hidden
  while the menu is open and reappears when it closes. This is the recorded rule for chrome-bar-anchored
  layers that would overlap the page rect.
- **Focus:** choosing an entry puts focus in the page; Esc closes the menu with no navigation and
  returns focus to the button that opened it.

### Home (NAV-04)

- Click on Home, or Alt+Home with the page focused, opens the home page in the active web tab;
  with no active web tab it opens a new web tab, which is how a pill commit already behaves.
- An empty `browser.homePage` opens the empty page and focuses the pill, as New Tab does.
- A non-empty value goes through the same address routing as a pill commit, so `https://…`,
  `http://…` and bare dotted hosts open. A value that routing rejects opens the Home-failure row
  below the pill; focus moves to the pill; Enter or a click on the row runs Settings filtered to
  the home-page setting; Esc closes the row.
- Home is never disabled.

### Tooltips (NAV-05)

- Rendered by Theia's `HoverService`, not by native `title=`. Native `title` tooltips are dead in
  the shell window until the `nsIXULBrowserWindow` shim lands in Phase 35, and keeping both would
  show two tooltips once that phase lands. The `title` attribute is therefore removed from the six
  nav buttons in this phase.
- **Layer policy, rule (c):** a tooltip never extends over the page rect. Each hover is requested
  at `position: 'top'`, so it sits over the row above the chrome bar (the menubar in Coding, the
  tab strip in Browsing, the toolbar in Organising, each at least 32px tall). It carries the class
  `pb-chrome-bar-hover`, which sets `--theia-ui-padding: 4px` and `line-height: 1.4` inside the
  chrome-bar `@layer`. A custom-property declaration on the element itself is not contested by
  stock CSS, so the layered rule takes effect. The hover then measures about 28px plus Theia's 5px
  gap, which fits the at-least-36px above a button, so `HoverService` never flips it down onto the page.
- Tooltips show on disabled buttons too (13-UI-SPEC: disabled keeps its tooltip).
- Stock hover delay; one line; no history-menu hint line.

### Middle-click and drop (NAV-06)

- **Middle-click** on Back or Forward opens that history step in a **new background tab** placed
  next to the current tab. Middle-click on Reload opens a duplicate of the current tab there.
  The current tab stays selected and focused, which is Firefox's default (`loadInBackground`).
  **Decided (autonomous, recommended), from Firefox:** Ctrl+click does the same as middle-click. The new tab
  joins the active group, as New Tab's does.
- **Drop on New Tab:** while an http(s) link (`text/uri-list` or `text/x-moz-url`, or plain text
  that is an http(s) URL) is dragged over New Tab, the button shows the drop-target ring (accent
  item 6) and the copy cursor. Dropping opens the link in a new **foreground** web tab, joined to
  the active group, with focus in the page. Anything else gets `dropEffect: 'none'` and no ring.
  Dropped plain text that is not a URL is searched in Phase 29, not here.
  Plain text cannot be classified while it is dragged (the drag data store is protected until drop),
  so a plain-text-only drag gets the copy cursor without the ring and opens at drop only when it is
  an http(s) URL (CONTEXT: Open Question 3 takes the research recommendation).

### Keys while a web page has focus (KEY-01..05)

**Rule (Chris, 2026-10-20):** a key that clashes with Theia takes the browser meaning **only while
focus is inside a web page**. Only Firefox's unblockable keys are reserved. Every other key uses
the reply path: the page sees the key first, and a page that consumes it keeps it, as in Firefox.
Page focus is pushed as a Theia context key. There is no visual page-focus indicator beyond the lit
active tab, which already exists, because Firefox shows none.

| Key (page focused) | Result | Where focus lands |
|--------------------|--------|-------------------|
| Ctrl+T | New Tab, identical to the button | Pill, empty |
| Ctrl+W | Close the current tab, no confirmation | The tab Theia activates next; inside its page if it is a web tab |
| Ctrl+R, F5 | Reload | Stays in page |
| Ctrl+Shift+R, Ctrl+F5 | Reload without cache | Stays in page |
| Esc (while loading) | Stop | Stays in page |
| Alt+Left / Alt+Right; mouse buttons 4 / 5 over the page | Back / Forward | Stays in page |
| Alt+Home | Home | Page (or pill, if the home page is empty) |
| Alt+D, Ctrl+L, F6, Shift+F6 | Focus the pill with its whole text selected (inherited focus ring) | Pill |
| Ctrl+Tab / Ctrl+PageDown | Next tab | That tab's page if it is a web tab |
| Ctrl+Shift+Tab / Ctrl+PageUp | Previous tab | Same |
| Alt+1 … Alt+8 | The nth tab; no-op when there are fewer | Same |
| Alt+9 | The last tab | Same |

- **Tab order** for the switching keys is the order the user sees: the tab strip in Browsing,
  and the tab bar holding the current tab in Coding and Organising. Next and previous wrap at both
  ends. No picker is shown (Firefox default: `ctrlTab.sortByRecentlyUsed` off).
- **From the pill:** F6 and Shift+F6 move focus back into the active web tab's page when there is
  one. **Decided (autonomous, recommended):** the pill is chrome rather than an editor, terminal or
  non-web tab, so KEY-04 does not apply to it. This makes F6 work in both directions, as in Firefox.
- **KEY-04, everywhere else:** in editors, terminals and every non-web tab, F5, F6, F11, Ctrl+P,
  Ctrl+K, Ctrl+Tab, Alt+Left/Right, Ctrl+W, Ctrl+R and the other clashing keys keep Theia's
  meaning, with no visible change of any kind.
- Opening a Theia popup from a key while the page has focus first moves focus to the Theia frame.
  Closing it restores focus to the page (layer-policy focus rule, Pitfall 8). In this phase that
  applies to Ctrl+T, which focuses the pill.
