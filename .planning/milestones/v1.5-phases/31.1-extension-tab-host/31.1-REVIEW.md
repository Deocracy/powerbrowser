# Phase 31.1: Code Review Report

**Reviewed:** 2026-10-30T08:20:00Z
**Depth:** standard (diff `bf8f3dd..ca492e8`, upstream behaviour read in `upstream/`, which holds the patched tree)

## Summary

Patch 050 is a properly regenerated patch. Each of its 10 `index` lines names the pristine blob (`git -C upstream rev-parse HEAD:<path>`), and `git apply` to those pristine bytes produces the post-image blobs the same lines name. No finding asks for a text edit of it.

The chrome-side host is correct against upstream on the paths I traced. These are tab-id minting and release (`ext-browser.js` `getId`, `_handleTabDestroyed`), the TabOpen/TabSelect/TabClose ordering against the deferred `emitCreated`/`emitActivated`, the `closing` flag that `emitActivated` reads, and the progress fan-out signatures. No defect found there, and no BLOCKER.

The weaknesses are in what the gates can prove. Three of the phase's load-bearing claims cannot go red as written: Theia absence from content scripts and `webRequest`, the page-focus selection hook, and the shape of the URL wall. The listener-cleanup path also lost the best-effort guard it used to have.

## Warnings

### WR-01: Theia-absence checks on events, requests and sender reports run over the probe's own narrow emitters, after Theia has loaded

**File:** `scripts/verify-ext-tab-host-live.mjs:1018-1088`, `:62`, `:71-83`, `:1149`; `scripts/lib/pb-relaunch.mjs:279-282`
**Issue:** `withShell` waits for `FrontendApplicationStateService.state === 'ready'` before `fn(app)` runs. `installProbe` and `waitForTheiaOrigin` run after that, so the Theia document is already loaded when the extension registers. Firefox does not inject manifest content scripts into already-loaded documents. The probe records only:
- `main_frame` requests;
- `hello` messages from its content script;
- tab events.

The Theia frame never navigates after install, so three of the four assertions in `absent()` can never be red for a Theia leak:
- `fromOther === 0` in `scenarioSender` (`:505`);
- `session.logs.some(... includes(theia.origin))` (`:1029`);
- the `tabIdsOf` check (`:1033`).

The only assertions that can fail are `getBrowserData(frame).tabId` and `tabs.query`. The `theia-in-tabs-late` plant is detected by `tabs.query` alone. No plant produces a Theia-named request, sender or event record, so nothing shows the record-based checks are able to see one. This is CLAUDE.md verification rule 1: an absence assertion over an emitter the check itself wrote. Nothing proves that `<all_urls>` content scripts and `webRequest` stay out of the IDE frame, which RESEARCH:269 and :330 name as the threat ("`<all_urls>` content scripts run inside the authenticated IDE"). In particular, `webRequest` listeners with `<all_urls>` can still be handed the frame's own requests with `tabId -1`, and the 31.1-02 SUMMARY's wording "out of every extension-visible path" is stronger than what is tested.
**Fix:** After install, reload the Theia frame and assert on records from that reload. For example, call `document.getElementById('powerbrowser-content').reloadWithFlags(...)` from chrome scope, then wait for Theia state `ready` again. Add `types: ['main_frame', 'xmlhttprequest', 'websocket']` to the probe's `onBeforeRequest`. Assert that no `request` or `sender` record names the Theia origin. Add a positive control in the same session: reload an overlay and require that its `request` and `sender` records arrive. Add a plant that sets `messagemanagergroup="browsers"` on the frame before the reload and requires the `sender` assertion to go red.

### WR-02: Nothing static pins the property the Theia exclusion rests on

**File:** `powerbrowser/shell/powerbrowser.xhtml:58`; `scripts/verify-ext-tab-host-scope.mjs:473`, `:481-488`, `:490-512`
**Issue:** D-06 and RESEARCH:108 state that the Theia frame stays out of content-script injection because it carries no `messagemanagergroup="browsers"`. The theia-exclusion family checks the other side only:
- `webTabOpen` sets the group on overlays;
- `tabHostAddTab` refuses a browser without it;
- the Theia identifier appears in the `gBrowser` literal only inside `webDriverTabs`.

No gate reads the `<xul:browser id="powerbrowser-content">` element or any `setAttribute("messagemanagergroup", ...)` elsewhere. Adding the attribute to the frame, in the XHTML or from `TheiaService`, leaves every gate green. It also defeats the `tabHostAddTab` guard, which tests exactly that attribute. WR-01 means the live suite would not catch it either.
**Fix:** Add a fifth scope family. Derive every `messagemanagergroup` occurrence under `powerbrowser/shell/` (XHTML attributes and `setAttribute` calls), and require that the only one is `webTabOpen`'s overlay literal. Give it a plant that writes the attribute into a staged `powerbrowser.xhtml`.

### WR-03: The page-focus and activation selection hooks are not pinned by any gate

**File:** `powerbrowser/shell/PowerBrowserAPI.sys.mjs:4670` and `:4889`; `scripts/verify-ext-tab-host-live.mjs:604-628`, `:678-681`
**Issue:** The 31.1-02 SUMMARY (deviation 6) and the 31.1-04 SUMMARY (deviation 12) record that `focus-follow` does not isolate page focus from Theia's current: focusing A also moves Theia's current to A, and Theia then sends `webTabActivated(A)`. The `focus-ignored` plant overrides the `selectedTab` getter. It does not remove `tabHostSelectById` from `pushPageFocus`, so deleting the page-focus hook leaves the scenario green through the other hook. The reverse is also true. `grep` finds no reference to `tabHostSelectById` or `pushPageFocus` in any `scripts/` file other than the live harness. The page-focus selection path (D-13) therefore has no check that goes red when it is removed.
**Fix:** Make the live scenario call `PowerBrowserWebTabs.pushPageFocus(frame, A.webTabId)` directly from chrome scope while Theia's current is the IDE (`webTabActivated(null)` was the last report). Assert that the active tab is A and that `activeTabByFrame` was not touched. Change the plant to replace `pushPageFocus` with a version that does not select. Add a static row to the scope gate requiring that `tabHostSelectById(` has exactly one call in `pushPageFocus` and one in the `webTabActivated` arm, as it already does for `tabHostAddTab`.

### WR-04: The URL wall is the one security hunk of 050 that no shape gate pins

**File:** `patches/050-extension-tab-host.patch:228-234` (ext-tabs.js hunk); `scripts/verify-ext-tab-host-scope.mjs:549-566`; `scripts/verify-ext-tab-host-patch-guards.mjs:66-99`
**Issue:** `wallFamily` verifies the wall by token presence in the added lines: `isTabHostWindow(nativeTab.documentGlobal)`, `url !== "about:blank"`, `Promise.reject` and the regex literal. It does not check how they combine. All four tokens survive each of these:
- `if (isTabHostWindow(...) || url !== "about:blank" && !/.../.test(url))`, which rejects every URL in a host window;
- `if (!windowTracker.isTabHostWindow(...) && ...)`, which applies the wall to stock windows and never to the shell;
- a changed operator.

The eight `GUARDS` rows have per-regex shape checks, a derived site and a weaken plant. The wall hunk has none. Its only protection is the live `wall-unkeyed` plant, which is not a `--quick` check.
**Fix:** Add a G9 row to `GUARDS`. Mode `before` with anchor `let options = {` in `tabs.update`, or mode `after` with anchor `let url = context.uri.resolve(updateProperties.url);`. Site `register.update`, or whatever the indentation walk derives. Regexes for the full `if (` shape, one per line of the multi-line condition. Add a WEAKEN entry that flips `&&` to `||`.

### WR-06: `tabHostDropTab` is unguarded in `webTabClose`; a throw skips `browser.remove()` and `webTabs.delete()`

**File:** `powerbrowser/shell/PowerBrowserAPI.sys.mjs:3851`, `:5728-5758`; caller loop at `:3907-3912`
**Issue:** The code this phase deleted wrapped the tab-record removal in `try/catch` with the comment "the element removal below is what frees the docshell". The replacement `tabHostDropTab(win, browser)` has no guard. It dereferences `node.ownerDocument.defaultView.CustomEvent` (`:5560`) and calls `host.strip.removeChild(node)` (`:5737`). Either can throw on a torn-down document or a node that is no longer a child, for example after the `theia-in-tabs` plant's `insertBefore`. A throw leaves the overlay's `<browser>` attached, its page still rendering, and the `webTabs` entry live. `webTabDropOwnedBy` (`:3907`) iterates every overlay a frontend owned and calls `webTabClose` with no catch, so one throw also abandons the rest. That loop is the T-14.1-05 containment ("pages still rendering and playing audio behind a shell that no longer knows they exist").
**Fix:**
```js
    try {
      tabHostDropTab(win, browser);
    } catch (err) {
      PowerBrowserAPI.log("error", `[web-tab] tab host drop failed: ${err && err.name ? err.name : "error"}`);
    }
    browser.remove();
    webTabs.delete(tabId);
```
Also use `host.win.CustomEvent` in `fireTabEvent` rather than re-reading `defaultView`.

### WR-07: `tabs.update` applies the URL, then rejects on the refused writes, leaving a half-applied update

**File:** `powerbrowser/shell/powerbrowser.js:85-87` (`set selectedTab` refuses); `upstream/browser/components/extensions/parent/ext-tabs.js:877-921`
**Issue:** `tabs.update(id, { url, active: true })` runs `fixupAndLoadURIString` at :903-905, which navigates, and only then reaches `tabbrowser.selectedTab = nativeTab` at :918. That assignment throws the `refuse()` error. The caller sees a rejection for a navigation that did happen. `pinned: true` (:945), `highlighted: true` (:926, :931) and `muted: true` fail the same way after the navigation, with a plain TypeError because those members are absent. The comment at powerbrowser.js:84 justifies the refusal because "a silent switch would answer wrongly". A partially applied write that reports failure also answers wrongly. This matters because the phase advertises `tabs.update` as the way extensions navigate, and `active: true` is a common property.
**Fix:** Preferably make `selectedTab`'s setter a no-op when `tab` is already `host.selected`, and refuse only a real switch. The common `{url, active: true}` call on the already-selected tab then succeeds. If that is rejected as too permissive, record in `DELIBERATELY_ABSENT` that the write order is non-atomic and test it, so a later phase does not rely on all-or-nothing.

### WR-08: The favicon is never cleared on navigation, and `setIcon` diverges from upstream's contract

**File:** `powerbrowser/shell/PowerBrowserAPI.sys.mjs:5796-5803`; upstream `browser/components/tabbrowser/content/tabbrowser.js:1362-1386`, `:9640-9657`
**Issue:**
- Upstream clears `browser.mIconURL` in `onLocationChange` when a new document starts loading (:9650-9657). The host's `attachProgress` never touches `node.image`, so after tab A moves from a page with an icon to one without, `tabs.get(...).favIconUrl` and `tabs.onUpdated` keep reporting the previous site's icon. The live `sender` scenario sets the icon once and never navigates.
- `makeString` (tabbrowser.js:1368) accepts an `nsIURI`. The host drops any non-string silently (`typeof url !== "string"`).
- Upstream refuses non-local icon URLs with a console error (:1372-1380). The host accepts any string.

**Fix:** In `attachProgress`'s forwarder, on `onLocationChange` with `webProgress.isTopLevel && webProgress.isLoadingDocument` and no same-document flag, set `node.image = null` and fire `TabAttrModified` with `changed: ["image"]`. In `setIcon`, accept `url instanceof Ci.nsIURI` via `.spec`, and apply the `chrome:`, `about:`, `resource:` and `data:` allow-list.

### IN-06: `tabs.highlight` fails with a TypeError rather than a refusal

**Issue:** `selectedTabs` is getter-only. `ext-tabs.js` is `"use strict"`, so assigning to it throws "setting getter-only property", not the `refuse()` sentence that the `selectedTab` and `addTab` stand-ins give. The stand-in gate cannot see the difference because the member name is satisfied.

### IN-07: Two empty `catch (e) {}` blocks in 050 swallow unexpected errors

**File:** `patches/050-extension-tab-host.patch:17`, `:323`
**Issue:** The `getTopNormalWindow` probe and the first `recent(null)` call catch everything, not only the documented `NS_ERROR_FAILURE`. A genuine bug in `isTabHostWindow` would be hidden. Whether that matters depends on how often the stock window is open.
**Fix:** Catch and rethrow unless `e.result === Cr.NS_ERROR_FAILURE`. Document the precedence in the hunk comment.

### IN-08: The `refuse()` text reaches WebDriver clients as "for an extension"

**File:** `powerbrowser/shell/powerbrowser.js:85-87`, `PowerBrowserAPI.sys.mjs:5806-5808`; `upstream/remote/shared/TabManager.sys.mjs:264-277`

That is an improvement over a hang, but the message names the wrong caller.
**Fix:** Keep as is, or pass the caller kind through. Not a gate concern.
