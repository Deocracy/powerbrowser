## Phase Boundary

Installed Firefox extensions see PowerBrowser web tabs as real tabs (query, events, active tab, tab ids on content scripts, webRequest and webNavigation), built on the route Chris signed off in Phase 28, so Phases 32-38 are built against it (ROADMAP.md Phase 31.1; requirement EXT-05 only).

In scope: patch `050-extension-tab-host.patch` regenerated from a patched tree (never text-edited) including the adversarial-check guards; the product tab host behind PowerBrowserAPI (one tab element per overlay, TabOpen/TabSelect/TabClose/TabAttrModified, tabs-progress fan-out, `gBrowserInit`, `selectedTab`/`selectedBrowser`, `getTabForBrowser` landing together); CHROME_TOOLBAR window-type fix; derived gates (browserWindows consumers as set equality, Theia frame never in the tracker, http(s)-only navigation guard against moz-extension://); `verify-shell-gbrowser-standin.mjs` rewritten for the new member set; D-74 amended for this one logic patch; the patch stack applied and the Gecko build run inside this phase, so success criteria 1-4 are proven live on that binary before the phase closes (D-11).

Not this phase, by cross-phase ruling X1 (2026-10-23): T-27-11 (the gBrowser stand-in call-site scope, actor registries) is owned by the committed Phase 35 plan 35-01 (`a85d973`), which edits the gate as 31.1-02 leaves it and records the closure. The ROADMAP scope line's "(closes T-27-11 todo)" is superseded by that ruling; ROADMAP.md is not edited from this phase directory.

Not in scope: EXT-06..10 (toolbar buttons, popups, page actions, AMO install, popular-extension checks) stay in Phase 38; no GUI-05; no chrome-bar UI; no `openStockPage` work (Phase 31); no find/zoom/mute members (Phase 32 adds them to the host); no new-window adoption (Phase 36).

## Implementation Decisions

### Recorded rulings that apply (REQUIREMENTS.md header, ROADMAP Phase 31.1, 28-SPIKE-DECISION sign-off 2026-10-21)
- EXT-04 is complete with Chris's sign-off; route (a)+(c) is locked: patch 050 opens the tracker gate AND a chrome-side tab host supplies the tabbrowser shape. No GUI-05.
- Sub-ruling 1 (Chris): while the IDE (editor/terminal) has focus, the last web tab stays the active tab for extensions (not "no active tab").
- Sub-rulings 2-3 (recommended defaults, taken with the route): extensions may not navigate an overlay to moz-extension:// pages (the http(s) rule holds); the Theia frame never enters the tracker, enforced by a derived gate.
- Policy changes carried: D-74 amended — the patch stack may hold this one logic patch; the 2026-10-20 ruling "getTabForBrowser keeps returning null" and the "never synthesise a tab" rule (powerbrowser.js:80-82) are reversed for the tab host only.
- Hard rules binding every row: no Theia core patch; Gecko changes only through patches/; Firefox internals only through `powerbrowser/shell/PowerBrowserAPI.sys.mjs` with catalogue rows; one driver `scripts/verify-platform.sh` with registry rows; derive-from-tree-and-compare with `--self-test`, never hand-kept lists, never absence assertions over an emitter the check does not control.

### Gray areas (auto-resolved, recommended option taken)
- **D-01: Patch authorship is regenerate-from-patched-tree, never text-edit the 002a draft.** Reason: text-editing a hunk degrades the 3-way merge into a silent no-op, which `apply-patches.sh` exists to catch.
- **D-02: The tab host lives behind PowerBrowserAPI; powerbrowser.js keeps only the `window.gBrowser` literal and the `extensiontabhost` attribute.** Reason: hard rule 2 allows exactly one boundary file, and extension parents calling the shell's gBrowser is inbound use, not a second boundary.
  - *Amended 2026-10-23 (mechanism, verified):* `window.gBrowserInit` is a new shim global, so under the Phase 27 shim policy it is defined in `PowerBrowserAPI.sys.mjs` (the host install), named in `FORBIDDEN_PATTERNS` with a self-test plant, and compared by `verify-shell-gbrowser-standin.mjs`. `powerbrowser.js` sets the attribute on the document element in its `DOMContentLoaded` handler (`powerbrowser.js:17-19`) right after the host install and the literal, so the window is admitted only once the shape exists: the trackers admit a window on its `load` event (`ext-tabs-base.js:1893-1905`, `:2124-2130`), which follows `DOMContentLoaded`. `powerbrowser.xhtml` is not edited.
- **D-03: `getTabForBrowser`, `selectedTab`/`selectedBrowser`, `gBrowserInit`, tab nodes and the first TabOpen land together in one plan.** Reason: `TabManager.getWrapper` reads them as one group, so landing them apart leaves a half-shape no gate can assert.
- **D-04: While the IDE has focus the host keeps the last web tab selected (Chris sub-ruling 1).** Reason: Chris decided it, and it avoids the null-selectedTab throw the adversarial check proved.
  - *Amended 2026-10-23 (mechanism):* selection is driven by D-13, not by overlay visibility. "The IDE has focus" means Theia reports no current web tab (`webTabActivated` with `tabId: null`, `web-tab.ts:742-772`); the host then changes nothing. `selectedTab` is null only when no web tab exists.
- **D-05: Overlays refuse moz-extension:// navigation (http(s) wall extended, not widened).** Reason: letting an extension page into a chrome-owned overlay would hand extension code a null-principal content process it did not expect.
  - *Amended 2026-10-23 (mechanism, verified):* the shell walls already refuse every scheme but http(s) and the empty page (`PowerBrowserAPI.sys.mjs:3241-3245` `webTabOpen`, `:3711-3715` `webTabNavigate`), but no extension call goes through them: `tabs.update({url})` loads straight into the tab's browser (`upstream/browser/components/extensions/parent/ext-tabs.js:875-896`, `browser.fixupAndLoadURIString`). Patch 050 therefore gains a hunk there that rejects any URL other than http(s) or `about:blank` for a tab in a tab host window, with upstream's own rejection shape (`:890`). See D-17 for what stays allowed.
- **D-06: The Theia frame (`#powerbrowser-content`) never gets a tab node and never enters `tabs`/`webDriverTabs`; a derived gate enforces it.** Reason: the missing messagemanagergroup on the frame is the load-bearing security property from spike 001, and only a gate keeps it so.
  - *Amended 2026-10-23 (B2): excluded from `tabs` and from every extension-tracker path only.* The Theia frame never gets a tab node, never appears in `tabs`, and never takes part in TabOpen, TabSelect, TabClose or TabAttrModified. It stays in `webDriverTabs`, the list patch 050's TabManager hunk gives to WebDriver alone (`upstream/remote/shared/TabManager.sys.mjs:189-199`). Reason: WebDriver is how BiDi and every live check reach the Theia frame (`app.evaluate`, today through `gBrowser.tabs`, `powerbrowser.js:56-62`). No extension code reads `webDriverTabs` (the exclusion gate derives that zero extension-scope files mention it). The security property is the frame's missing `messagemanagergroup` (`powerbrowser.xhtml:58`, spike 001), and `webDriverTabs` leaves it unchanged. The `webDriverStillReachesTheia` control in VALIDATION is that positive control.
- **D-07: Patch 050 grows the two adversarial-check guards before it lands: an `ext-pageAction.js` null-selectedTab guard and a TabOpen null-linkedBrowser guard; hunk/file/rebase counts are re-derived in the build plan.** Reason: the skeptics proved the 7-file draft never starts a page_action extension at zero tabs, which is how the shell starts every launch.
  - *Amended 2026-10-23 (W1, verified):* the TabOpen guard goes in the TabOpen branch of `TabTracker.handleEvent`, at the `currentTab` read: `upstream/browser/components/extensions/parent/ext-browser.js:543-548` (`const currentTab = nativeTab.documentGlobal.gBrowser.selectedTab; const { frameLoader } = currentTab.linkedBrowser;`). Lines 557-562 are the deferred `emitCreated` callback, and they are not the guard site. `currentTabSize` is optional (`emitCreated` `:714-722`; `_handleWindowOpen` passes none, `:640-642`), so the guard leaves it undefined when there is no frame loader. The pageAction guard is the `browserWindows()` loop at `ext-pageAction.js:169-174`. D-14 adds the rest.
- **D-08: The CHROME_TOOLBAR window-type fix lands in the host plan, not the patch plan.** Reason: it is shell-side `windowtype` furniture (`WindowBase.type` popup-vs-normal), not tracker-gate logic.
  - *Amended 2026-10-23 (mechanism, verified):* `openShellWindow` passes null arguments, so `nsWindowWatcher::OpenWindow` treats it as a non-dialog (`nsWindowWatcher.cpp:286`). `all` applies only to dialogs (`:1961-1963`), so the shell gets no `CHROME_TOOLBAR` (measured `chromeFlags = 2150630918` = `0x80300606`, 002a trail 5). A `toolbar` feature sets the bit (`:1972-1974`), and `WindowBase.type` then reports `normal` (`ext-tabs-base.js:1080-1092`). The fix appends `toolbar` to the `openShellWindow` features string (`PowerBrowserAPI.sys.mjs:1027-1035`). `openBrowserWindow` passes an argument, so it is a dialog and gets `all`; it stays unchanged.
- **D-09: `verify-shell-gbrowser-standin.mjs` is rewritten for the tab-host member set (closes T-27-11 open item); the old null-stand-in DELIBERATELY_ABSENT record is retired with reasons.** Reason: the member set it asserts is replaced by the host, so extending the old gate would assert a shape that no longer exists.
  - *Amended 2026-10-23 (X1):* the rewrite covers what the host changes, and no more:
    - a second call-site scope, the extension parents (`upstream/browser/components/extensions/parent/ext-*.js` plus `toolkit/.../parent/ext-tabs-base.js`), where every member access counts;
    - receivers widened to `getTabBrowser()` results, which the host makes non-null for overlays (`toolkit/content/widgets/browser-custom-element.mjs:950-955`);
    - the `gBrowserInit` shim.

    It does **not** widen the actor scope to the actor registries, and it does not close T-27-11. Both belong to Phase 35 plan 35-01, which edits the gate as 31.1-02 leaves it. The two old `DELIBERATELY_ABSENT` reasons that rest on `getTabBrowser()` being null (`getNotificationBox`, `removeTab`) are rewritten, because the host reverses that premise.
- **D-10: New browserWindows() consumers get a derived set-equality gate in this phase.** Reason: every new upstream consumer of `browserWindows()` is otherwise a silent regression, per the 002a fidelity note.
  - *Amended 2026-10-23 (verified):* the scope covers every non-test `*.js`/`*.mjs` under `upstream/browser/components/extensions/` and `upstream/toolkit/components/extensions/`, `addOpenListener` call sites included. At the pinned tag that is 18 `browserWindows()` call sites and 6 `addOpenListener` call sites, counted during planning; the gate derives them. 002a's enumeration missed `toolkit/components/extensions/ExtensionShortcuts.sys.mjs:310, :329, :337`, `ext-browser.js:1297` and the three tracker-internal sites in `ext-tabs-base.js` (`:1900`, `:2046`, `:2085`).
- **D-11: Live proof runs in this phase on a rebuilt binary with patch 050 applied (EXT-05 success criteria 1-4 plus GUI-01 still green); Phase 38 reuses the same suite, it does not re-prove it.** Reason: SUMMARY.md requires every prompt/furniture item to start from a recorded live probe, and the route was only ever runtime-emulated.
  - *Amended 2026-10-23 (B3):*
    - Plan 31.1-01 Task 3 resets `upstream/` to the pin, replays the stack with `scripts/apply-patches.sh`, and runs the full `./mach build` inside `nix develop .#firefox`.
    - Every later live run first checks that build stamp, and its preflight checks that the running binary carries 050.
    - Plans 31.1-02 and 31.1-04 run the live scenarios.
    - No task may finish with a live row marked pending.
    - If 050 is regenerated after that build, the apply and build steps run again before any live row.
- **D-12: No UI-SPEC for this phase.** Reason: EXT-05 has no user-visible surface; the host, patch and gates are chrome-side only.
- **D-13 (2026-10-23): Host selection follows Theia's selected web tab and page focus, not overlay visibility.** Two hooks select a tab, and a null from either changes nothing (D-04):
  - the `webTabActivated` arm (`PowerBrowserAPI.sys.mjs:4501-4507`; the frontend sends it on every change of the main area's current title, `web-tab.ts:742-772`);
  - `PowerBrowserWebTabs.pushPageFocus` (`PowerBrowserAPI.sys.mjs:4612-4620`, called from the focus tracker at `powerbrowser.js:396`).

  Reason: `webTabActivated` means "selected, not merely visible", so a split view does not move the selection between two visible overlays. Once `getTabBrowser()` is non-null, `SelectParent.sys.mjs:316-320` and `AutoCompleteParent.sys.mjs:214-219` suppress the select picker and the form-fill popup in any overlay that is not `selectedBrowser`, so selection must follow the overlay the user types in.
- **D-14 (2026-10-23): Patch 050 covers 10 files after verification against the pinned tag.** The 002a seven, plus:
  - `ext-pageAction.js`: the D-07 null guard in the `:169-174` loop, plus a tab-host skip at the top of `updateButton` (`:199-230`). Without the skip, `PageActions.sys.mjs:1214-1219` throws for any window that has no `BrowserPageActions`, once a selected overlay matches `show_matches`.
  - `toolkit/components/extensions/ExtensionShortcuts.sys.mjs`: the sidebar-shortcut line `:432-434` skips tab-host windows. `window.SidebarController` does not exist in the shell, and the throw would stop `registerKeys` (`:309-312`) before later windows. Extension keysets otherwise stay in the shell, as Phase 38 plan 38-05 expects.
  - `ext-tabs.js`: the D-05 URL wall in `update` (`:875-896`), and a tab-host skip in the `onZoomChange` registration loop (`:1330-1338`). That loop reads `ZoomManager`, which the shell lacks (`:1320-1322`), and would otherwise fail every `tabs.onZoomChange` registration, stock window included, while the shell holds a web tab.

  The `getTopNormalWindow` hunk is also corrected so it cannot throw. Upstream returns null when no window matches (`browser/modules/BrowserWindowTracker.sys.mjs:207-240`), but the draft calls `this.getTopWindow(context)`, which can throw `NS_ERROR_FAILURE` (`ext-tabs-base.js:1804-1809`). Reason: each is a derived per-window consumer or extension load path that breaks in the shell or bypasses the shell wall. Phase 32 drops the zoom skip when it lands the zoom host members (ROADMAP Phase 32 notes).
  - *Amended 2026-10-23 (checker W3, I1, verified):* the `onZoomChange` registration also installs a `tabCreated` listener (`ext-tabs.js:1340-1345`, registered for `tab-created` at `:1384`) that calls `getZoomLevel`, and so reads the shell's missing `ZoomManager`, for every web tab opened. `ExtensionCommon.sys.mjs:337-345` catches the throw and reports it as a chrome error. 050 therefore also skips tab-host tabs at the top of `tabCreated` (guard G8), so 31.1-04's chrome-error recorder can assert no error. Phase 32 plan 32-09 drops G8 together with the loop skip when it adds the shell zoom shims. The URL wall uses the shell walls' own allow-list regex, `/^https?:\/\//i`, so one literal governs both paths.
- **D-15 (2026-10-23): The live suite has no "host not admitted" control run.** Each scenario carries a plant that must go red naming its expected text, and each absence assertion has a positive control in the same session, recorded by the same recorder. Reason: in the product, the attribute is set before the window's `load`, so the trackers can admit the window before the script's first step. A runtime removal cannot restore today's state, and there are no test hooks in product code. 002a's `results-control.json` stays the historical baseline.
- **D-16 (2026-10-23): The host exposes no `tabContainer` or `visibleTabs` member.** The strip element stays internal: it is each tab node's `parentNode`, which `TabTracker.setId` requires (`ext-browser.js:391-397`). Reason: no `gBrowser` receiver in either call-site scope reads either member at the pinned tag, so the derived gate would flag them as DEAD SURFACE. Phase 35 plan 35-02 forbids a `tabContainer` reference in the shell section, and Phase 37 builds its own PopupNotifications facade.
- **D-17 (2026-10-23): D-05 covers every navigation that chrome or an extension API starts** (the two shell walls and `tabs.update`). A page navigating itself to a web-accessible extension resource stays allowed. Reason: that load runs in the extension's process under the extension principal, exactly as in Firefox, and no chrome-owned path or null principal is involved.
- **D-18 (2026-10-23): This phase adds no `webTab*` kind and no store kind.** It reuses `webTabActivated` (already classed `selection` in `scripts/verify-web-tab-bridge.mjs:74`). Reason: EXT-05 needs no new frontend message; the bridge gate's set equality goes red on any arm added without a class.
