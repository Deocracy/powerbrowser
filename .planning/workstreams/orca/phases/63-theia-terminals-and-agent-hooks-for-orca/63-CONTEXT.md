## Implementation Decisions

### Theia-backed PTY provider (TERM-01, criterion 1)
- **P63-01 (Claude's pick): PB's provider is a new overlay class `PowerBrowserTheiaPtyProvider extends LocalPtyProvider`; only the node-pty module beneath it is replaced, by a node-pty-compatible facade whose PTYs live in Theia's backend.** Reasons from the pinned source: `configureLocalPtyProvider` configures the provider only when `localProvider instanceof LocalPtyProvider` (`orca/src/main/ipc/pty/provider/local-configure.ts:40`), and that call is where `buildPtyHostEnv` adds the hook environment, terminal handle and runtime stamps (`local-configure.ts:43-150`); `LocalPtyProvider` and its helpers (`orca/src/main/providers/local-pty/`, about 10.4k lines) carry env finalisation, shell-ready wrappers, foreground inspection and termination that a from-scratch provider would have to copy. A subclass has every required `IPtyProvider` member by inheritance, gets the hook env for free (P63-14), and moves the re-pin exposure from `IPtyProvider` (changed in 9 of 21 releases, D-28) to node-pty's `IPty`, a published third-party interface. This keeps D-28's intent (all required members, not five operations) and amends D-01's wording "a fifth implementation beside Local..." to "a subclass of Local with a Theia-backed PTY layer". — **Reversibility:** costly; Chris may prefer a from-scratch `implements IPtyProvider` class, which keeps the same seams, bridge and checks. *(Superseded by P63-20: no PB provider class.)*
- **P63-02 (Claude's pick): two new declared seams, both in the PTY-provider category, each a short env-switched branch; the overlay then carries 3 of the 10-seam cap (S1 is Phase 62's).** S2 in `src/main/orcad/orcad-daemon-supervision.ts` (`startOrcadDaemon`): when the switch is set, import the PB provider file, call `setLocalPtyProvider(new PowerBrowserTheiaPtyProvider())` and return without starting the daemon. S3 in `src/main/providers/local-pty/local-pty-runtime-spawn.ts` (`loadLocalPtyRuntimeSpawn`): when the switch is set, import the PB facade instead of `node-pty`. Reasons: orcad starts the daemon at `orcad-entry.ts:75` through `startOrcadDaemon` → `initDaemonPtyProvider` → `replaceDaemonProvider` → `setLocalPtyProvider` (`daemon/daemon-provider-state.ts:99-101`), so a seam in `registry.ts` or `daemon-provider-state.ts` (the files D-16 names) would come after the daemon process already exists; no existing switch disables the daemon (grep of `process.env.ORCA_*DAEMON*` at the pin); node-pty is loaded for the local provider only at `local-pty-runtime-spawn.ts:15`. Neither file is part of the mobile-facing protocol (D-23, D-29). The switch is one fixed name set by `OrcaEnv`, `ORCA_PB_THEIA_PTY_ENDPOINT` (the endpoint-file path, P63-03), following P62-14's `ORCA_DISABLE_INSTALLED_ELECTRON_BROWSER`. — **Owner-visible:** the two seam files are not the examples D-16 lists; each stays within P62-17's 20-line bound. *(Seam shapes superseded by P63-21.)*
- **P63-03 (Claude's pick): the transport between orcad and Theia is a Unix domain socket served by the Theia backend, found through an endpoint file, with no secret in any process environment.** The pattern copies Orca's own `ORCA_AGENT_HOOK_ENDPOINT` file design, and the rule copies `theia/extensions/token-gate/src/node/powerbrowser-env.ts` and `TheiaService.sys.mjs:820-836` (environ is readable by same-uid processes for the life of the process, so no credential goes there). Chrome picks the directory `<short runtime dir>/pty-bridge/` (mode 0700, same location rules as P62-19's alias: `$XDG_RUNTIME_DIR` first, never `/tmp`) and passes only the path: to Theia as `POWERBROWSER_ORCA_PTY_DIR` (captured and deleted at module load like every `POWERBROWSER_*` key) and to orcad as `ORCA_PB_THEIA_PTY_ENDPOINT=<dir>/endpoint.json`. The Theia backend creates the socket (0600) and writes `endpoint.json` (0600: socket path, a 256-bit token, protocol version) at start; the orcad side reads the file at each connect and reconnects after a Theia restart. Framing is newline-delimited JSON control frames plus data frames. The message set is defined once in the Theia extension (`src/common/`) and once in the overlay; a check compares the two sets (P63-17). Windows named pipes and macOS socket paths are Phase 68.
- **P63-04 (Claude's pick): the Theia side is one new extension `@powerbrowser/orca-terminals` (`theia/extensions/orca-terminals`), and its bridge server core is a plain Node module with no Theia DI.** A thin `BackendApplicationContribution` wraps the core and spawns each PTY through `@theia/process`'s `TerminalProcessFactory`, so every PTY is in Theia's `ProcessManager` and a frontend `TerminalWidget` attaches with `start(id)` (`theia/node_modules/@theia/terminal/lib/browser/base/terminal-widget.d.ts:68`). The PTY gets exactly the environment orcad's provider sends (the env `LocalPtyProvider` built); the bridge adds and removes nothing. The plain core lets checks host the bridge under Node with node-pty and no Theia. No Theia core file is edited (hard rule 1; `scripts/diff-theia-core.sh` stays green). *(Spawn path amended by P63-28: `OrcaTerminalProcess` subclass, not `TerminalProcessFactory`.)*
- **P63-05 (Claude's pick): orcad's node-pty startup probe keeps running unchanged and must pass, so `build-orca.sh` keeps building node-pty for Node 24 (Phase 60) even though the provider no longer spawns through it.** The probe runs before `main()` (`orca/src/main/orcad/main.ts:96-110`, `node-pty-precondition.ts:181-250`); the criterion-1 row runs orcad with `--orcad-native-preflight` (name derived from `src/shared/orcad-native-preflight-report.ts:3`) and requires status `ok`. With the switch, `health.terminalDaemon.state` must read `absent` (`orcad-health.ts:94-122`); without it, `live`.

### Terminal identity and tabs
- **P63-06 (Claude's pick): the bridge mints the Theia identity `o<n>` (lowest unused index, as `allocateName` does for `t<n>` in `theia/extensions/tab-uris/src/browser/terminal-naming-contribution.ts`), keeps the map `o<n>` ↔ Orca PTY id ↔ Orca terminal handle ↔ Theia process id in the backend so it survives a frontend reload, and opens the widget with `terminalIdentityOptions('o<n>')`, addressable as `terminal:o<n>`.** `TERMINAL_NAME_PATTERN` (`/^t(\d+)$/`) is untouched, so user terminals and Orca terminals never share a name. `TerminalUriOpenHandler`'s stale-name rule (D-48: create a fresh shell under that name) is exempted for `o<n>`: a stale Orca name opens nothing and logs, because a plain shell must not pose as an Orca terminal. `TabUriRegistry`'s exported shape is unchanged (`verify-registry-shape.mjs`); `docs/URI-SCHEMES.md` gains the `o<n>` row. Phase 64 maps `pb-orca:` panes onto these widgets. *(Restore path amended by P63-28: widgets open with `kind: 'orca'`.)*
- **P63-07 (Claude's pick): every PTY spawned through the bridge opens one Theia terminal tab in the main area (D-01: Orca tabs are dock tabs), without taking focus, titled from Orca's pane title or the terminal's OSC title.** A PTY Orca marks hidden at spawn (the field is a research item; `orca/src/main/ipc/pty/pty-hidden-at-spawn-mark.test.ts` names the concept) is mapped and addressable but not opened. Until Phase 64 removes Orca's own terminal view, the Orca client and the Theia tab can both resize the same PTY; the last request wins, and this is recorded as a known limit, not fixed here. *(Hidden-at-spawn exception and title source superseded by P63-22.)*
- **P63-08 (Claude's pick): input and output take two paths.** Keystrokes in the Theia tab go straight to the Theia process; writes from orcad (`terminal.send` from Orca clients and the CLI, agent startup commands) go over the bridge. PTY output is delivered to both: to the widget through `ProcessManager`, and to orcad as bridge data frames, with Orca's `acknowledgeDataEvent` flow control mapped to the facade's pause/resume. Which `IPty` internals `LocalPtyProvider` reads beyond the public typings (for example `getForegroundProcessGroup`, read defensively in `orca/src/main/pty/process-retirement/pty-master-foreground-observation.ts:20-40`, and the pts name) is a research item; a missing one must degrade to Orca's existing "older native image" path, not fail. *(Research items resolved by P63-23.)*

### Lifecycle (D-07 revised)
- **P63-09 (Claude's pick): Theia's backend owns every Orca PTY, so agents end when PowerBrowser quits through the existing paths:** `TheiaService` stops the sidecar, Theia's `ProcessManager` kills its processes on stop, and `OrcaService` stops orcad. Phase 62's `stop()` and its reap must accept `health.terminalDaemon.pid === null` (no daemon exists with the switch set). The RUN-05 quit and SIGKILL checks (62's `orca-service-live`) are extended to the Orca PTYs under the Theia backend: before quit, record each provider-created PTY's process and its descendants; after quit, none alive. After a SIGKILL of PowerBrowser the Theia parent-death watchdog ends the backend and the PTY masters close; the relaunch check requires those pids gone.
- **P63-10 (Claude's pick): when orcad's bridge connection drops while Theia lives (an orcad crash or respawn), the bridge kills that connection's PTYs after a short grace period, and the Theia tabs stay open showing the exit.** orcad cannot re-adopt in-process PTYs: `canRecoverPersistentLocalPtys` reads `daemonOwnsFreshPersistentPtys()` (`orcad-entry.ts:211`), which is false with no daemon. When Theia restarts, the provider reports an exit for every PTY with `hostLost` (`pty-provider-contract.ts:236`).

### Remote hosts (TERM-03, D-20)
- **P63-11 (Claude's pick): SSH and paired-server PTYs stay on their own paths (`registry.ts:73-78` throws for any non-local host), and their Theia tabs are pseudo-terminals in `@powerbrowser/orca-terminals` fed by orcad's runtime RPC (`terminal.subscribe`, `terminal.send`, `terminal.resizeForClient`), with the Theia backend acting as a paired client of PB's own orcad.** Streaming methods are served only on orcad's WebSocket and are authorised by per-device tokens (`orca/src/main/runtime/runtime-rpc/runtime-rpc-websocket-dispatch.ts:103`); the CLI's Unix socket is request/response (`orca/src/cli/runtime/transport.ts`). The Theia backend therefore pairs once per orcad start and keeps its device credential in memory, or in a 0600 file in the 0700 data root, never in an environment variable or a log (RUN-07 floor). The pairing step and the remote-handle naming are research items; remote tabs use the same `o<n>` identity map (P63-06). — **Reversibility:** costly; the alternative is to wait for Phase 64's hosted client and render remote panes from its connection. *(Superseded by P63-24.)*
- **P63-12 (Claude's pick): the SSH live check runs against a throwaway user-mode `sshd` on a loopback high port** (OpenSSH from the Nix dev shell, scratch host key and authorized key, no system configuration change; this host has no running `sshd`). The paired-server check runs a second PB-run orcad with a scratch data root and a free port, paired as a runtime host of the first (PB-to-PB, allowed by D-20). Both are live rows under the live lock, Linux only (D-24). *(Superseded by P63-24: no `sshd` row; one paired-server regression row in the coordinator plan.)*

### Keys (TERM-04, D-09)
- **P63-13 (Claude's pick): `@powerbrowser/orca-terminals` registers `KeybindingRegistry.PASSTHROUGH_PSEUDO_COMMAND` for `ctrl+w`, `ctrl+t`, `ctrl+tab`, `ctrl+shift+tab`, `ctrl+pageup` and `ctrl+pagedown`, with the `when` clause `powerbrowser.orcaTerminalFocus`, a context key that only Orca terminal widgets set.** This is the mechanism `chrome-bar-keybindings.ts:85-89` already uses for the address pill. It is needed because Theia core binds `ctrl+tab` to `NEXT_TAB` with no `when` clause (`theia/node_modules/@theia/core/lib/browser/common-frontend-contribution.js:794-796`). No chrome change: with the Theia frame focused, chrome's page-key rows are disabled (`powerbrowser/shell/powerbrowser.js:494-503`), so the keys already reach Theia. The bindings use literal `ctrl`, not `ctrlcmd`, so on macOS Cmd keeps PowerBrowser's tab commands and Ctrl reaches the terminal. Ctrl+Shift+Tab is included as the reverse of Ctrl+Tab; D-09 names only Ctrl+Tab. User `t<n>` terminals keep their current bindings. *(`when` clause and context key superseded by P63-25.)*

### Agent hooks (TERM-02, EXT-02)
