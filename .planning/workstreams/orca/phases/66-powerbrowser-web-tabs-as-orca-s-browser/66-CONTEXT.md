## Phase Boundary

A browser page that Orca or an Orca agent opens is a PowerBrowser web tab with PB's chrome bar, address field and history, and Orca's stock screencast pane and its entry points are never shown (BRW-02). Orca agents drive those tabs through a chrome-side bridge that reaches only Orca-created tabs, and the shipped build listens on no WebDriver BiDi port (BRW-03). While an agent drives a tab, the Theia chrome bar shows an "agent is controlling this tab" mark with a Stop button; stock browser windows are unchanged (BRW-04). The user-facing tools of Orca's browser, as spike 005 inventories them, are reachable from PB's chrome bar or a Theia side panel (BRW-05). Success criteria are the four in ROADMAP Phase 66. This phase also carries the clause Phase 62 moved here: "PB's orcad completes a browser request without launching the decoy" (`62-VERIFICATION.md`, deferred item 1).

The route is fixed by Phase 61 (spike 005, VERDICT YELLOW): S2, a PB runtime client that attaches through `browser.clientHost.attach` with no Orca patch and builds the tier-1 set of 50 abilities (25 BiDi, 9 BiDi+, 14 native, 1 actor for `snapshot`, `exec` as a documented subset); S1 (a 13-line provider-kind patch) stays the fallback. The five YELLOW conditions (`.planning/spikes/005-orca-browser-parity/README.md` VERDICT, `61-VERIFICATION.md` "Spike 005 to Phase 66") are binding here and each has a pick: (1) a PB-owned runtime client, not the proof's two reaches past Orca's public surface (P66-02); (2) the 85 `[ASSUMED]` rows are estimates, and the Q3 and Q5 probes run before the rows that depend on them (P66-04, P66-14, P66-15); (3) Q4 is decided before any BiDi or BiDi+ row is built (P66-11); (4) `snapshot` is its own piece of work (P66-16); (5) one `browserPageId` maps to exactly one PB-created tab (P66-05). The spike's owner note stands: S2 reverses P61-05 (owner item, end-of-milestone pass).

Depends on Phase 64 being merged, not only planned: the `@powerbrowser/orca-panes` route table with its pending `browser` row (P64-01), the offer handover through the `pty-bridge` directory (P64-07), the Theia backend file route that serves Orca bundles (P64-06), and Orca's renderer observed in the Theia document (P64-08, P64-13). Out of scope: grab and annotate into an agent prompt (BRW-06), markup on screenshots (BRW-07), dev-server tiles on the new-tab page (BRW-08), agents sharing the user's browsing profile (BRW-09); tier-2 and tier-3 abilities (uploads, downloads through the file channel, interception, emulation, profiles, storage, `find`, `highlight`); the failure page, pairing containment, the Origin check and the landing logo (Phase 67); packaging and the weekly re-pin job (Phase 68).

## Implementation Decisions

### Runtime client and pairing (condition 1, BRW-03)
- **P66-01 (Claude's pick): the S2 runtime client runs in the Theia frontend, in a new extension `@powerbrowser/orca-browser` (`theia/extensions/orca-browser`); it is not in the Theia backend and not chrome-side.** The client is only the protocol end; the bridge that acts on pages is chrome-side (P66-06, P66-11), which is what BRW-03 and D-11 name. Reasons from the tree: every web-tab overlay is owned by the frontend's actor and is closed when that actor goes (`webTabDropOwnedBy`, `powerbrowser/shell/PowerBrowserAPI.sys.mjs:4297`), so a client that outlives the frontend would hold pages that no longer exist; the frontend already holds the web-tab channel the client must call (`WebTabChannel.widgetOf`, `theia/extensions/tab-uris/src/browser/web-tab.ts:653`), and the proof ran there (`results-proof.json`: `theiaOrigin` loopback, `secureContext: true`, attach accepted); the Theia backend has no channel to chrome overlays and would relay through the frontend anyway; a chrome-side client would need Orca's paired E2EE client compiled into chrome JS, outside the overlay build and the brand rows. — **Reversibility:** cheap until the lanes start; the backend alternative adds a relay hop and no capability.
- **P66-02 (Claude's pick): the client is PB-owned and thin, built over Orca's shared modules, not over `WebRuntimeClient`; it is compiled by Orca's toolchain from PB-added overlay files and served by the Theia backend, never from orcad's port.** It uses `createPairedE2EEClientHandshake` with its own `clientCapabilities` argument (`orca/src/shared/paired-e2ee-client-handshake.ts:63`, `:136`), which removes reach 1 (the proof appended `browser.clientHost.v1` to the frozen `WEB_RUNTIME_CLIENT_CAPABILITIES` constant, `s2-host.ts` header note 1); it opens one connection and issues the attach subscription and every `browser.clientHost.commandResult` on that same connection, which removes reach 2 (the proof called the private `subscribeOnCurrentConnection`, `orca/src/renderer/src/web/web-runtime-client.ts:209`). Not importing `web-runtime-client.ts` also keeps the 19.3 MB web-client graph out of the bundle (spike README, S2 cost 2). The entry and a PB Vite library config live under `orca-overlay/files/` and are built by a new `scripts/build-orca-browser-host.sh` called from `scripts/build-orca.sh`, as P64-01 builds the pane bundle; the bundle file reaches the Theia backend through the `pty-bridge` directory file pattern and is served by P64-06's backend route (S2 cost 3: orcad serves only `/web-index.html` and four prefixes). If research shows the thin client cannot attach without a private member, the fallback is two small upstream exports offered under D-27 (Phase 68), not a seam. — **Reversibility:** cheap; the client is PB files only.
- **P66-03 (Claude's pick): the client pairs with the offer P64-07 already hands to the frontend and attaches at frontend start whenever orcad is ready, in every mode.** It takes the offer from the same Theia JSON-RPC call the pane bundle uses (never a URL, environment variable, log or user-visible text), and it opens its own connection, separate from the pane bundle's client (spike 004 measured two clients on one orcad, `results-route-b-prime.json` `secondClientSeesTab: true`; spike 005 Q7). Attach parameters are those the proof used: capability `browser.clientHost.v1`, host capabilities `webview` and `automation-v1`, page-command, inventory and reconciliation protocol version 1, `authorityRuntimeId` from `status.get` (`orca/src/main/runtime/rpc/methods/browser-client-host.ts:21-40`). Reason: agents run in Theia terminals whatever the mode, and orcad starts eagerly (P62-02), so an agent's `orca goto` must find a host without the user opening the Orca mode.
- **P66-04 (Claude's pick): `/gsd-plan-phase 66` research runs bounded probes before any plan is written, and their results fix the dependent picks.** Under the live lock, with the spike 005 harness (`provider-proof.mjs`, `scripts/lib/pb-live-probe.mjs`): Q3 (P66-14), Q5 (P66-15), a Q4 feasibility pass for the actor and native mechanisms of P66-11 on one row each (a click through the agent child, a screenshot through `drawSnapshot`), whether one offer admits two paired clients or the host needs its own pairing, how the renderer's `createBrowserTab` (`orca/src/renderer/src/store/slices/browser/browser-tab-actions.ts:38`, 17 caller files) reaches orcad and the host's `createPage` in the web build, which host call reports a page the user closed (the call Orca's `ClientHostedBrowserPagePane` makes on a dead guest), the console mechanism (P66-11), and the reference fixtures for `snapshot` (P66-16). Each probe records its result in `66-RESEARCH.md` with the run evidence. Reason: condition 2 says the `[ASSUMED]` rows are estimates until probed; probing in research keeps the lanes on a measured route.

### Tab ownership (condition 5, BRW-03, criterion 2)
- **P66-05 (Claude's pick): the client holds one page table, `browserPageId` to web-tab id, and enforces one-to-one in both directions.** `createPage` opens a new PB web tab and records the pair; a `createPage` for a mapped id, or a second id for a mapped tab, is answered `failed` and creates nothing; `closePage` closes the mapped tab and drops the pair; `navigate` (the non-automation command type) uses the existing `webTabNavigate` kind on the mapped tab; `reclaimPage` and `restorePage` are answered from the table and never adopt a tab the client did not create (command types at `orca/src/shared/browser-client-host-protocol.ts:207-254`). Every command for an unmapped id is refused with an Orca error code chosen by research from the existing set (`browser_tab_not_found` is the default). The table is in memory only; the attach `pageInventory` reports exactly the mapped pages. Reason: spike README S2 cost 4, "the proof's host maps every page to the one tab it opened".
- **P66-06 (Claude's pick): the chrome-side wall is the second, independent layer: a tab is an agent tab only if it was created with an `agent` flag, and every agent kind refuses any other tab.** The frontend sends the flag in `webTabOpen` for a new tab id only; `PowerBrowserAPI.webTabOpen` (`:3568`) records it on the host entry at creation and never sets it later (an `already-open` reply ignores it), so no request can turn a user's tab into an agent tab. Agent kinds look up `webTabs` only, so a stock browser window's tabs are unreachable by construction, and each kind answers `not-agent-tab` for a user tab, `unknown-tab` for an unknown id and `agent-stopped` after Stop (P66-22). Reason: the frontend document also runs Orca's renderer code (P64-07), so the frontend's table cannot be the only wall; chrome is the component that acts on pages.
- **P66-07 (Claude's pick): an Orca-created tab opens in the background and never takes focus.** It is added to the main area after the active Orca pane of the page's worktree when one is open, else at the end, through `WebTabOpenHandler` (`web-tab.ts:1610`, the `openInBackground` placement pattern at `:1724`) extended with the `agent` option on `WebTabOptions` (`:160`); the address field and history are the tab's own, as for any web tab. Reason: inventory row U-10 (agent input focus guard) and Q3; an agent must not move the user's keyboard focus.
- **P66-08 (Claude's pick): a user's close of an Orca tab is Orca's page close, and a frontend reload ends the client's pages.** A Lumino close of a mapped web tab closes the overlay as today and the client reports the page closed through the call research names (P66-04). A frontend reload closes every overlay (`webTabDropOwnedBy`) and the client's connection; the new client attaches with an empty inventory and orcad's own recovery releases the old pages (`recoverUnavailableRuntimeBrowserClientPages`, imported at `browser-client-host.ts:15`). Reason: the overlay lifetime already follows the frontend; keeping orcad's records for pages that no longer exist would leave the agent driving nothing.

### Agent mark and Stop (BRW-04, criterion 3)

Reason: the component that executes the commands and enforces the wall is the one whose state can be trusted.
- **P66-21 (Claude's pick): the mark is a chrome-bar element beside the sharing indicator, with a Stop button, plus a title mark on the tab itself.** It is rendered by a `renderAgentControl()` method next to `renderSharing()` (`theia/extensions/chrome-bar/src/browser/chrome-bar-widget.tsx:1663`, placed at `:1887`) for the current web tab only, so it appears for PB web tabs and never in a stock browser window, which has no chrome bar. ### Privacy and egress
- **P66-26 (Claude's pick): Orca-created tabs load in their own container (a `userContextId` reserved for Orca agents), so agents do not share the user's cookies, storage or logins.** The overlay gets the `usercontextid` attribute before it is appended, in the attribute list of `webTabOpen` (`PowerBrowserAPI.sys.mjs:3592-3602`); the container identity is created once through a new `PowerBrowserAPI` method with its catalogue row; the cookie rows act only inside that container.
