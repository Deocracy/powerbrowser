<interfaces>
Probed live first (.mozbuild/p66-09/probe-1.txt, probe-2.txt, on the unmodified tree):
  - Download: an agent page's click on a PDF attachment saved the file and opened a stock window
    (chrome://browser/content/browser.xhtml). With SANDBOXED_DOWNLOADS set on the overlay's browsing context: no file,
    no window; Gecko logged IframeSandboxBlockedDownload. The web progress states of the two cases are identical and
    the console message carries window id 0, so neither can tell chrome; an http-on-stop-request of the agent overlay's
    document channel with status NS_ERROR_ABORT can (nsExternalHelperAppService.cpp:1640-1645 cancels with it).
  - External protocol: an agent page's click on a custom scheme opened chrome://mozapps/content/handling/permissionDialog.xhtml
    as a standalone window. ExternalProtocolIsBlockedBySandbox returns false for a top-level browsing context, so a
    sandbox flag cannot cover it; LoadURI does do_CreateInstance("@mozilla.org/content-dispatch-chooser;1") per load.
  - First document: a tab created without a URL is on a navigated (non-initial) about:blank with the flags, and
    window.open threw. A tab created for a URL whose headers are held stays on its initial about:blank
    (isInitialDocument true); there browser.mouseClick then browser.eval of window.open with features opened a stock
    window and loaded the page. nsDocShell gives the initial document InitialSandboxFlags (nsDocShell.cpp:6619-6622),
    which has no webidl setter, so the gap closes by refusing commands, not by moving the flag write.
Error code: browser_command_unavailable (Orca's BrowserErrorCode is a closed union in a tracked Orca file; D-35).
</interfaces>
