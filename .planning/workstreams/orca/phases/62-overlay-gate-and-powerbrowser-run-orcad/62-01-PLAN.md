Tree facts this plan relies on (verified while planning):
- regenerate-patches.sh write mode regenerates only patches that already exist: it reads each
  patch's diff --git headers to learn its paths (patch_paths), diffs those paths against HEAD in the
  --upstream tree and replaces the file. A new patch is therefore started as a one-line seed holding
  only the diff --git header, then regenerated. Both it and apply-patches.sh refuse an empty patch
  directory ("contains no *.patch files"), so every caller guards on the patch count.
- apply-patches.sh accepts --upstream orca (orca/ is its own git top level and not this checkout),
  applies with git apply --3way (which stages the result) and refuses a no-op by blob hash.
- git -C orca rev-parse HEAD:src/main/orcad/orcad-browser-provider.ts prints
  90b79e505d8db41a8cf61cb45dd41f36658a6966 at the pin 965978bc; orca/ is a shallow clone and
  rev-parse, ls-tree, cat-file and diff HEAD all work on it.
- installedElectronCandidates(platform, homePath, environment) is at orcad-browser-provider.ts:71;
  resolveInstalledElectronExecutable passes process.env as environment (line 116).
- fetch-orca.sh's verify path checks HEAD and the tag only, so an applied seam does not fail it.
- Rows are "label|command"; only the exit code maps to PASS/FAIL; a SKIP is a printed line and exit 0.
</context>
