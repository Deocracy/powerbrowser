## Behaviour changes
- 59-CR-01, 59-CR-02, packaging-prefs-network-01 (54-04 runner-user libvirt access, 54 BLOCKED.md item 6): the release runner unit now creates its work directory and a persistent podman store, and pb-runner is no longer in libvirtd (no runner job reaches qemu:///system; whoever runs win-matrix-run.sh sets LIBVIRT_DEFAULT_URI). For that runner only it overrides these module defaults, each because rootless podman under release.yml's calls needs it: RestrictNamespaces=false (podman creates user, mount, network, UTS, IPC and PID namespaces); PrivateUsers=false (newuidmap maps pb-runner's subordinate ranges, absent from a private user namespace); NoNewPrivileges=false (newuidmap and newgidmap are setuid); CapabilityBoundingSet=mkForce [CAP_SETUID CAP_SETGID] (the module's empty set leaves the setuid helpers without the capabilities a multi-range id map needs); PrivateDevices=false (the private /dev has no /dev/fuse for fuse-overlayfs and no /dev/net/tun for pasta, podman 5's default rootless network, which `podman run` uses since release.yml passes no --network); DeviceAllow=mkForce ["" "/dev/fuse rw" "/dev/net/tun rw"] (ProtectClock implies char-rtc, and a non-empty list closes every other device); RestrictSUIDSGID=false (unpacking image layers recreates setuid files); ProtectHostname=false (crun calls sethostname); ProtectKernelTunables=false and ProtectKernelLogs=false (their locked over-mounts under /proc make the kernel refuse the procfs mount crun makes in the container's user namespace); SystemCallFilter=mkForce (the module's list minus ~@mount, ~capset and ~sethostname); ReadWritePaths for the podman store. PrivateMounts, ProtectProc and ProtectControlGroups stay at the module default.
  The security trade (also in the unit file's header): compared with the module default, build code on this runner can now create unprivileged user, mount and network namespaces, the usual starting point for kernel privilege-escalation exploits; run host setuid programs, which keep CAP_SETUID and CAP_SETGID through the bounding set; create setuid files; see host files and processes under their real uids (PrivateUsers off; ProtectProc stays "invisible", so other users' /proc entries stay hidden); and see the full /dev tree (opening a device is still limited to the pseudo devices, /dev/fuse and /dev/net/tun). Nothing opens a direct path to the registration token (still InaccessiblePaths) or to /home (still ProtectHome). This is the price of running rootless podman under this unit, and it is why the Orca build should run inside the container (lane G5a is doing that) or off this host (the held branch). Not deployed; the first deployment is the proof. Revert with 9166941e, 80835ebf and 543925f1.
