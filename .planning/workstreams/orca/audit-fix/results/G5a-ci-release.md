     - Residual risk. A container on a persistent host is a weaker boundary than a hosted runner. The rootless container still shares with legion:
       - the kernel (one kernel exploit escapes);
       - the runner user's identity (container root is pb-runner on the host, so a breakout lands as pb-runner, beside the runner's registration state);
       - the checkout, mounted read-write, which later host steps execute. Only the drop to orcabuild keeps Orca's code from writing it; the Gecko build and packaging containers run with write access;
       - the network, through the rootless network helper, which can reach the host's loopback services unless that is disabled;
       - the runner service's sandbox, which systemd/legion-pb.nix relaxes for rootless podman (RestrictNamespaces, PrivateUsers, NoNewPrivileges, PrivateMounts, PrivateDevices with /dev/fuse, RestrictSUIDSGID, ProtectHostname, ProtectProc, a narrowed SystemCallFilter), and those relaxations apply to every process of the runner, the host steps included;
       - the persistent podman store under /var/lib/pb-runner-data, which survives jobs; the images are rebuilt with --no-cache --pull=always.
     - G5b's record says the unit is not deployed and its first deployment is the proof.
