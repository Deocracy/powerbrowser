## Blocker

### BL-01: the watchdog dedupes on title alone, so any GitHub account can silence it

**File:** `docs/watchdog.yml:75` (and the "open issue = dedupe" claim at :61-62)
**Issue:** `OPEN_COUNT` counts any open issue in powerbrowser-updates whose title equals
`release-train has not run in 26 h`, regardless of author or label. Both repositories are public with issues
enabled (checked with `gh api`). An anonymous account opens one issue with that title and the watchdog never opens
its own again, for as long as that issue stays open, including when the train really is silent. This is the same
class as the maintenance-issue fix (905e6f38) that the orchestrator already treated as a security fix, applied to
the one monitor that sits outside the product repository. A legitimate watchdog issue the owner never closes has
the same effect (no re-alert on a second outage).
**Failure scenario:** attacker (or noise) opens the titled issue; the Worker clock then stops; no watchdog issue
is created; the only external check on the train is mute.
**Fix:** count only bot-authored issues, and let the gate require it:
```bash
OPEN_COUNT=$(gh issue list --repo "$GITHUB_REPOSITORY" --state open --author "app/github-actions" \
  --search 'in:title "release-train has not run in 26 h"' --limit 100 --json title \
  --jq '[.[] | select(.title == "release-train has not run in 26 h")] | length')
```
Also create the issue with a fixed label, filter on it too, and add a `checkWatchdogText` rule plus a plant
("dedupe counts issues by any author") to `verify-watchdog.mjs`. Optionally, close or comment on the previous
watchdog issue when the train is healthy again, so a second outage re-alerts.

## Warnings

### WR-01: the sweep runs on every dispatch tick from 06:00 to 23:59 UTC, not once a day (diverges from must_haves)

**File:** `.github/workflows/release-train.yml:451-478`, `scripts/release-train.mjs:555-557`
**Issue:** 48-03-PLAN.md:117 and 48-RESEARCH.md:222 define the gate as "now UTC is at or past 06:00 **and no sweep
ran today**". `sweepDue` is only `getUTCHours() >= 6`, and the Worker dispatches hourly, so 18 sweeps a day run.
Each live one enters the `bot` environment (an approval wait if the environment has reviewers, which the
`bot-job-gate` rule text assumes, and the `release-train` concurrency group does not cancel in progress, so a
waiting sweep blocks the whole train), mints an App token, and POSTs one synthetic event to the production Worker
(18 D1 rows a day). The docstring calls repeated ticks "idempotent", which is true of the issue writes but not of
the probe or the approvals.
**Fix:** make `sweep-clock` return true only for the first tick at or past 06:00 UTC that has not swept today.
The cheapest stateless version: due when `hour == 6` (the Worker ticks hourly), or read the previous state
artifact's date (already restored in `report`, so move the date check there or store `sweptOn` in `state.json` and
have `sweep-clock` look it up). Add a self-test control for "second tick the same day is not due".

### WR-02: the synthetic-POST row cannot detect a wrong or missing secret, and BLOCKED.md item 6 says it can

**File:** `.github/workflows/release-train.yml:542-553`, `worker/events-worker.mjs:221-238`, `BLOCKED.md` item 6
**Issue:** `handleEvents` honours `synthetic: true` only when `authorized()` passes, and otherwise stores the event
as a normal row and still answers 200 (`ok: stored 1`). With an empty, rotated-out or mismatched
`DOWNLOAD_COUNT_SECRET` the probe gets 200, the row goes green ("marked synthetic and excluded from maintainer
queries"), and a `MaintenanceProbe` event lands in the maintainer view every tick. BLOCKED.md says the probe "fails
closed (status not 2xx, a red row) when the value is wrong"; that is false. The 48-03 prohibition (synthetic row
marked synthetic and excluded) is violated silently in exactly the misconfiguration the rotation row in RENEWALS.md
anticipates.
**Fix:** have the Worker report what it did (for example `ok: stored 1 synthetic 1`) and make the probe require it
(`curl -sS ... | grep -q 'synthetic 1'`, status 0 otherwise), or fail the step when `SHARED_SECRET` is empty and add
a 401-versus-200 check against `/download-counts`, which does fail closed. Correct the BLOCKED.md sentence.

### WR-03: any probe failure removes the whole sweep, so a missing App grant leaves the pinned issue stale and silent

**File:** `.github/workflows/release-train.yml:513-523, 556-558`
**Issue:** `maintenance` runs only when the probe result is `success` or `skipped`. The runner step has
`set -euo pipefail` and no `|| true`, and the token mint step fails if the App lacks the requested
`administration`/`actions` permission (BLOCKED.md item 2 is exactly that state). A 403/5xx on the runner count then
fails the job, `maintenance` is skipped, `report` skips every maintenance step, and the pinned issue is not
refreshed and nothing is posted. Unrelated rows (esr-pin-age, which is the actual release-health row) go dark with
it. The comment above the watchdog step promises a failed read "renders red rather than failing the probe", which
is only true for that one step.
**Fix:** make each probe step tolerate failure (`continue-on-error: true` on the mint and read steps, or
`|| true` and empty output), let `maintenance` run on `failure` too, and render the unobserved rows as `no-data`
(runner) or `red` (watchdog), as the code already does for empty outputs.

### WR-04: the pinned issue is found with a 200-item client-side filter, so strangers can push it out of the window

**File:** `.github/workflows/release-train.yml:706-713`
**Issue:** `gh issue list --search 'in:title "..."' --limit 200` returns the 200 newest matches of any author and
the owner/label filter runs afterwards in JS. In a public repository 200 same-titled issues by anyone push the
owner's pinned issue out of the result; the plan then takes the `create` path (writes nothing, prints "owner pins it
at plan 48-05"). Fail-safe in the sense that nobody gets write access, but the sweep stalls silently.
**Fix:** narrow server-side: add `--author "$OWNER_LOGIN" --label release-train` (put `OWNER_LOGIN` in this step's
`env`; when it is empty skip the call and write `[]`). Keep the JS filter as the second check.

### WR-05: `esr-pin-age` fails open when the commit-date lookup fails

**File:** `.github/workflows/release-train.yml:589-596`, `scripts/release-train.mjs:446-447, 456`
**Issue:** a failed `gh api commits/$SHA` (rate limit, transient 5xx, `awk` finding no SHA) is swallowed
(`2>/dev/null || true`, `[ -n "$DATE" ] && ...`), so the tag has no entry in `tagDates`; `esrPinRow` then
`continue`s past it as "not stale" and reports green with the evidence "none older than 3 days without a
published Release", a claim the sweep did not observe. The row's whole purpose is to go red when a newer ESR tag
sits unreleased; a read failure turns that into green. The self-test has no plant for a newer tag with no date.
**Fix:** when a tag newer than the pin has no date, return `no-data` ("commit date of <tag> unavailable"), never
green; add that plant. Also note that the date used is the commit date of the tag target, not the tag's creation
time, so it can be older than the tag and turn the row red early; if a tag date is available from the tag object,
prefer it.

### WR-08: the live-delivery analyzer validates only `event.data`, and 8 of its rules have no plant

**File:** `scripts/verify-telemetry-live-delivery.mjs:64-134, 176-218`
**Issue:** (a) The leak checks run over `ev.data` keys only. An event `{kind, name, data: {...admitted},
message: "...", stack: "..."}` or a body with an extra top-level key passes; I called `analyzeCapture` with
exactly that and got `[]`. The gate exists to prove "no message, stack, path or URL rides the body", so it should
inspect the whole parsed envelope, and also scan the raw body for the drill's own message text (`pb-drill-`).
(b) The doc header says an unhandled rejection carries no position, but `REJECTION_KEYS` only requires keys and
nothing forbids `source/line/column` on a rejection (the same call above sent `line: 3` on the rejection:
accepted). (c) The "real envelope" is only as strict as the producer: the key set and shapes come from the
producer's own `ADMITTED_KEYS`/`admittedValueOk`, and captured events are never run through the Worker's
`admitEvent`/`handleEvents`, so a sender/Worker contract drift is invisible even though the Worker module is
already imported for `corsHeaders`. (d) Mutation: with each of the following rules removed the self-test stayed
green: missing preflight, content-type, event kind, value shape, required keys, no rejection event, no uncaught
event, non-JSON body. The six plants cover only the data-key rules, "no POST", "empty" and "level off".
**Fix:** check `Object.keys(ev)` equals `kind,name,data,at` and `Object.keys(body)` equals `events`; assert no
position keys on the rejection; run each captured body through `handleEvents` with a stub DB and require 200 and one
stored row per event. Add one plant per rule above (POST without OPTIONS, `text/plain`, `kind: 'usage'`, `line:
'12'`, event missing `buildID`, only the uncaught event, only the rejection event, body `not json`, top-level
`message`).

### WR-09: the PATCH decision compares raw API body bytes to the rendered body

**File:** `scripts/release-train.mjs:171` (via `findExactlyOne`), `.github/workflows/release-train.yml:706-713`
**Issue:** `patch = found[0].body !== rendered.body`. The owner creates the pinned issue by hand (BLOCKED.md item
1), and the web UI stores `\r\n`; GitHub may also trim a trailing newline from a stored body, while `renderMaintenance`
ends with `\n`. If either normalisation happens, every due tick sees a byte difference and edits the issue (up to
18 edits a day, polluting the edit history) and "PATCH only on a byte diff" fails. The self-test uses
identical-byte fixtures so cannot see this. I could not confirm GitHub's trailing-newline behaviour offline.
**Fix:** compare `norm(a) === norm(b)` with `norm = s => s.replace(/\r\n/g, '\n').trimEnd()` in `nextMaintenance`
(keep `findExactlyOne` as is for the tracking writer), and add a CRLF and a trimmed-newline control.

### WR-10: `watchdog-age` reads the newest watchdog run of any conclusion, so a permanently failing watchdog shows green

**File:** `.github/workflows/release-train.yml:525-540`
**Issue:** `runs?per_page=1` returns the latest run regardless of status or event. The watchdog fails the job (red
run, no issue) whenever its read of the product repository fails, and the file's own header warns about that for a
private repository; a failing-every-day watchdog still has a run started under 26 hours ago, so the row stays green
while MON-01 is dead. A manual `workflow_dispatch` also resets it. The `2>/dev/null || true` also turns a 403 on
this very read into "no watchdog run recorded", which is the wrong diagnosis.
**Fix:** `.../runs?per_page=1&status=success` (and `event=schedule` if the intent is the daily tick), and print the
read error to the log instead of discarding stderr.

### WR-11: the bot probe token holds Administration read and Actions read on both repositories

**File:** `.github/workflows/release-train.yml:496-511`
**Issue:** one `create-github-app-token` call carries `permission-administration: read` and
`permission-actions: read` for `powerbrowser` and `powerbrowser-updates`. The runner count needs Administration only
on `powerbrowser`; the watchdog read needs Actions only on `powerbrowser-updates`; so each repository gets one
unneeded scope, and Administration read (repo settings, runner registration state, branch protection, webhooks
configuration) is broad. Today the runner row renders `no-data until Phase 49` for any count of zero, so the grant
buys nothing yet.
**Fix:** mint two tokens (or drop `administration` until Phase 49 registers a runner), each scoped to the single
repository and the single permission, and pass each only to the step that needs it. Update BLOCKED.md item 2
(owner grants) to match.

### WR-12: the drill rewrites a tracked file in place with no signal handling, and rebuilds a development bundle over the tree

**File:** `scripts/verify-telemetry-live-delivery.mjs:296-342`
**Issue:** `theia/applications/browser/package.json` is overwritten with the loopback endpoint and restored in
`finally`. A `Ctrl-C`/`SIGTERM`/OOM during the two multi-minute builds skips `finally`, leaving the loopback URL in
a tracked file that can be committed (and the working tree is shared with other sessions per project memory). The
restore rebuild runs `theia build --mode development`, replacing whatever bundle was there. If the first rebuild
does not pick up the rewritten endpoint, the drill's errors go to the production endpoint (the run would then fail
only as "no capture").
**Fix:** register `SIGINT/SIGTERM` handlers that restore the original bytes synchronously; write the rewrite into a
copy of the application directory or an env override rather than the tracked file; assert in the drill that the
bundle contains the marker before driving the page (before the restore) so a stale bundle fails early and never
reaches the network.

## Info

### IN-01: the report job reads workflow runs and artifacts without an `actions: read` permission

**File:** `.github/workflows/release-train.yml:645-653, 721-756`
`permissions` is `contents: read` and `issues: write`. On a public repository these reads work; if the repository
goes private (or GitHub changes how cross-run artifact downloads authorise), `maint-prev` and `maint-restore` fall to
the fail-safe path silently and the red comment repeats on every tick. Add `actions: read` (a read scope) or note
why it is not needed. Also check that `verify-workflows` `issues-write`/permission rules accept it.

### IN-02: a re-run attempt conflicts with the first attempt's artifact, and a failed run's state is lost

**File:** `.github/workflows/release-train.yml:811-819`
`upload-artifact` without `overwrite: true` returns 409 on a re-run of a run whose first attempt already uploaded
`release-train-maintenance-state`. Separately, a run that posts the red comment and then ends `failure` (another job
failed) uploads a state that `selectStateRun` correctly refuses, so the next successful run re-comments the same
transition. Add `overwrite: true` and accept the duplicate as the documented cost of fail-safe notify.

### IN-03: `per_page=10` on the run list can starve the lookup

**File:** `.github/workflows/release-train.yml:733`
Non-due and dry-run ticks on `main` are successful runs with no artifact; the 06:00 tick sees six of them between it
and the previous sweep, and `self`/`owner` dispatches add more. Ten is enough for hourly ticks today but nothing
asserts it. Raise it to 50 or filter by `created` date.

### IN-04: untrusted text reaches the pinned body and the comment unchecked

**File:** `.github/workflows/release-train.yml:628-629`, `scripts/release-train.mjs:456`
`FIREFOX_ESR` from product-details is put into the evidence as is (it can contain a newline, `@name`, or markdown),
and evidence lines are copied into the red-transition comment. Mozilla is a trusted source, but validate it against
`^[0-9]+(\.[0-9]+){1,2}(esr)?$` before use, and strip newlines from every evidence string in `renderMaintenance`.

### IN-05: watchdog hardening

**File:** `docs/watchdog.yml:34-38, 19, 41-61`
`actions/checkout` and `contents: read` are unused (the job reads no repo file); dropping both leaves `issues: write`
as the only scope, which the gate already tolerates. The 26-hour limit is applied to a daily schedule, so a run
delayed more than about two hours (common for GitHub `schedule:`) turns the sweep's `watchdog-age` row red falsely.
GitHub also disables scheduled workflows after 60 days without repo activity; the watchdog-age row is the only
cross-check and is noted in 48-RESEARCH.md as an open probe.

### IN-06: probe request hygiene

**File:** `.github/workflows/release-train.yml:546-553`
The endpoint is read from `configuration.toml` and receives the bearer secret with no `https://` assertion; `curl`
has no `--max-time` (a hang burns the 10-minute job timeout and, via WR-03, kills the sweep); the secret is on the
`curl` argv (masked in logs, visible in `ps`). Add `--max-time 20`, require `https://` before sending, and pass the
header via `-H @file` or `--config`.

### IN-07: smaller gate gaps

**File:** `scripts/verify-watchdog.mjs:130-138`, `scripts/verify-platform.sh:4905-4917`
`checkProductSchedules` uses `/^\s*schedule\s*:/m`, so `on: [push, schedule]` passes (verified; `verify-workflows`
`no-schedule` parses YAML and covers it, so this is a duplicate rule, but it is the weaker one). The registry rows
`release-train-logic-self-test` and `release-train-maintenance-self-test` run the identical command, so the
second row cannot turn red independently, unlike the plan's "maintenance self-test half". `FORBIDDEN`,
`UNCAUGHT_KEYS` and `REJECTION_KEYS` in the analyzer are hand-kept lists next to the producer's key set (CLAUDE.md:
derive and compare).

### IN-08: operator-facing text

**File:** `.github/workflows/release-train.yml:788-792`, `scripts/release-train.mjs:669`
With `OWNER_LOGIN` unset or case-mismatched against the author login, the plan takes the `create` path and the log
says "the owner pins it at plan 48-05" although the issue exists. Print that the owner variable is unset or matches
no open issue, and compare logins case-insensitively on both sides (GitHub logins are case-insensitive) while still
requiring an exact owner match.
