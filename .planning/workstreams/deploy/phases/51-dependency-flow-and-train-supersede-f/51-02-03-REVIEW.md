## Blockers

### BL-01: `supersededMark` bypasses the revision guard, so CR-01 is not fixed for a labelled chemspill train

**File:** `scripts/release-train.mjs:269-282` (`supersedeCause`), `:293-306` (`derive`), `:322-326` (`supersedeTarget`)
**Issue:** The revision check wraps only the two flag arms. The last line, `return f.supersededMark === true ? 'marked' : null`, runs
for any revision, any state and any facts. Probe results:

```
revision 2 (chemspill) openPr + supersededMark                 -> SUPERSEDED (cause marked)
revision undefined + supersededMark                            -> SUPERSEDED
release key v153.5.0-2, BUILDING, supersededMark               -> SUPERSEDED, target {runId: 9}
release key malformed ("v153.5.0"), BUILDING, supersededMark   -> SUPERSEDED, target {runId: 9}
no candidate, no PR, nothing, supersededMark                   -> SUPERSEDED
```

`derive`'s own doc comment and RELEASING.md say "a chemspill revision train is never superseded, whatever flags the collector
sets". That holds for flags but not for the mark. One `state/SUPERSEDED` label on the revision-2 key's issue (a stray human click,
a writer that stamps the wrong issue, a duplicate-issue mix-up) makes a security revision derive SUPERSEDED, page nobody, and
hand the executor the run id of its release build. The fail-safe comment ("a missing or odd revision counts as a revision, so
nothing irreversible follows") is false for the same reason: an odd revision plus a mark is superseded and irreversible.
**Fix:** Apply the revision test to the mark too, and require a train to exist:
```js
const isScheduled = (f.openPr || rel !== null) && revision === 1;
if (!isScheduled) return null;
if (f.chemspillOpen === true) return 'chemspill';
if (typeof f.newerTag === 'string' && newerOnSameLine(f.newerTag, own)) return 'newer-esr';
return f.supersededMark === true ? 'marked' : null;
```
Add controls: revision 2 + mark, malformed key + mark, no-train + mark each derive their ordinary state (or null).

### BL-02: The grouped Dependabot actions PR will fail the exact-pin verifiers for `anthropics/claude-code-action` on its first run

**File:** `.github/dependabot.yml:29-32` (group `patterns: ["*"]`); pins at `scripts/verify-workflows.mjs:142,463` and `scripts/verify-triage.mjs:83,266`
**Issue:** `verify-workflows` (fixer-pin) and `verify-triage` (pin) require `anthropics/claude-code-action@db77d4d3...` (v1.0.254) byte for
byte. `triage.yml:85` carries that pin, and Dependabot's `github-actions` ecosystem will bump it: the latest release is v1.0.266 today
(`gh api repos/anthropics/claude-code-action/releases`), the pin is a SHA of a tagged commit so Dependabot can resolve it. The bump
lands in the same single `actions` PR as `actions/checkout` and the rest. The required check `verify` (ruleset `main-review`) goes red
on the `workflows` and `triage` rows, so the one PR AUTO-03 exists to produce cannot merge, every week, and the model-bearing action
is the one the owner most needs to bump by hand with its tool allowlist re-reviewed (FIX-08). The temptation is to bypass the gate. The
other admission rules (`sha_pinning_required`, `patterns_allowed` as `owner/repo@*`) do survive a Dependabot SHA bump; this exact pin
does not. `@dependabot recreate` re-adds the bump.
**Fix:** Exclude it from Dependabot and keep re-pinning a deliberate act:
```yaml
    ignore:
      - dependency-name: "anthropics/claude-code-action"
```
(`exclude-patterns` in the group would only turn it into a separate red PR.) Add a line to dependabot.yml and RELEASING.md saying the
fixer pin moves by hand together with the two verifiers.

## Warnings

### WR-01: The mark has no provenance contract, and it outranks every other state

**File:** `scripts/release-train.mjs:269-282`, `:293-306`, `BLOCKED.md` item 10, `release-train.mjs:419-425` (`findExactlyOne` doc)
**Issue:** Answer to the question asked: a non-owner cannot add `state/SUPERSEDED` unless they hold triage or write on the repository.
The triage workflow cannot add it either: `triage.yml:135-137` filters its allowlist to `^(type|os|format|area)/`, so neither
`release-train` nor `state/*` is reachable from untrusted issue text. So the exposure is narrow today. But the fact is a bare boolean
with no source requirement: item 10 lists what the collector must pass (`run.id`, `environment.id`, `newerIssueUrl`) and says
nothing about who authored the issue or who applied the label. The release tracking issue is found by "label-and-title" (doc of
`findExactlyOne`), while the maintenance issue is found by `selectPinned`, which requires `author.login == ownerLogin`. Reading a
label gives no authorship at all (it needs the issue events API, `labeled` event actor). No collector exists, so nothing enforces
any of this when it is written. Separately, because `derive` returns SUPERSEDED before the BUMP_RED / CONFLICT / stage rules
(`:303`), a marked train hides a real failure that would page: probe, `merged + pinUnchanged + supersededMark` -> SUPERSEDED,
`stage: FAIL apply` + mark -> SUPERSEDED. The header comment `:58-59` ("the tracking issue is a view, never an input") is now false
for two inputs (`issueState` already, and the mark).
**Fix:** In item 10 require: the issue is found by label and title and its `user.login` is the bot App or the owner; the label's
`labeled` event actor is the bot App; otherwise `supersededMark` is false. Order the mark after the failure rules (or make it apply
only to states that are not BUMP_RED/CONFLICT/LIVE_RED). Change the header comment.

### WR-02: Stickiness turns any transient fact, including a chemspill that already shipped, into a silent permanent stall

**File:** `scripts/release-train.mjs:278-281`, `:121`; `docs/RELEASING.md` (supersede paragraph, "stays set ... even after the chemspill train publishes")
**Issue:** `chemspillOpen` is a transient fact by nature: the chemspill revision publishes and the scheduled ESR train should then
proceed. With the mark it never does. The scheduled train's `chore/esr-<newer tag>` PR stays open, `detect` sees "candidate with open PR
= pr-open" and starts no new bump, the key derives SUPERSEDED (routine, no page, link-only action), and nothing tells the owner the
ESR update is dead until someone reads a `state/SUPERSEDED` label. The same applies to a single false positive on `newerTag` (a bad
tag listing): the writer stamps the label once and the correct train is dead for good. There is also no documented way back (removing the
label is not mentioned, and the issue is `lock: true`). Stickiness is right for cause `newer-esr` (that train is obsolete) and wrong
for cause `chemspill`.
**Fix:** Persist the cause: mark only a train superseded by a newer ESR as sticky, let a chemspill-superseded train return to
BUMP_PR_GREEN (or to a distinct paged state, "resume after chemspill") once the chemspill train publishes. Document the owner
procedure to clear a mark. Add a control for the chemspill-then-published case.

### WR-03: `supersedeTarget` hands the executor a run id for a BUILDING run, which may be mid-publish

**File:** `scripts/release-train.mjs:322-326`, `:300`
**Issue:** `BUILDING` is any in-flight run (`RUN_IN_FLIGHT`), including a `sign-publish` job after the approval was spent, past the
bot token mint and while the draft Release or the assets are being created. `supersedeTarget` returns `{runId}` for it. A cancel by run
id then races publication: the `published === null || draft` test (`:299`) is a snapshot, not a lock, and the Release is immutable once
published. The safe action for AWAITING_APPROVAL is rejecting the pending approval (`environmentId`); a run past approval is already
protected by the two sign guards, which exist for exactly this. Item 8 does not warn the owner.
**Fix:** Return a cancel target only for AWAITING_APPROVAL (`environmentId` set, run `waiting`). For BUILDING return null (link-only) and
let the guards fail the run. State this in BLOCKED item 8.

### WR-04: dependabot.yml has no `cooldown`, and the zizmor gate never sees the file

**File:** `.github/dependabot.yml:21-40`; `scripts/verify-zizmor.mjs:68` (runs zizmor over `.github/workflows/` only)
**Issue:** `zizmor --offline .github/dependabot.yml` (zizmor 1.29.0, the pinned version) reports two `dependabot-cooldown` findings
(medium, confidence high), one per ecosystem: "insufficient implicit default-days (less than 7)". The `zizmor` row passes because it is
pointed at the workflows directory, so the finding is invisible to the gate; the repo rule forbids suppressing zizmor findings, and this one is
real: a weekly Dependabot PR that adopts an action release minutes after publication is the compromised-release window (a SHA pin only
protects until Dependabot rewrites it). The summary calls the file validated against the SchemaStore schema, which does not check this.
**Fix:**
```yaml
    cooldown:
      default-days: 7
```
on the `github-actions` entry (cooldown does not delay security updates, so the npm entry needs none, but zizmor still asks for it; add
it there too). Point the zizmor row at `.github/` (or add `.github/dependabot.yml` as a second target) so the file stays audited.

### WR-05: The grouped PR bumps actions that no pull-request check ever runs, including majors

**File:** `.github/dependabot.yml:29-32`; `.github/workflows/release.yml`, `release-train.yml` (`workflow_dispatch` only)
**Issue:** `upload-artifact`, `download-artifact`, `attest-build-provenance`, `create-github-app-token` and a second `checkout` use are
used in dispatch-only workflows. `verify.yml` (the only PR gate) exercises none of them at runtime; `verify-release-shape` and
`verify-workflows` check structure, not behaviour. A group without `update-types` includes major bumps (artifact actions have had breaking
majors; `release.yml` also runs jobs on the self-hosted `legion` runner, whose runner version caps which Node runtime an action may
require). A green merged PR then fails for the first time at release time, after the approval is spent.
**Fix:** `update-types: ["minor", "patch"]` in the group so majors arrive as separate PRs the owner reads, and record in RELEASING.md
that a merged actions bump is exercised only by the next release.

### WR-06: The "npm security-only" half cannot go red

**File:** `.github/dependabot.yml:33-40`; `scripts/verify-repo-controls.mjs:714-732`; BLOCKED item 12
**Issue:** Security-only depends on two things nothing reads: the `automated-security-fixes` switch (the summary probed it:
`{"enabled":true,"paused":false}`) and `open-pull-requests-limit: 0` itself. If the switch is turned off, or someone raises the limit to
5, every check stays green: with the switch off, no npm PR is ever opened and nothing says so; with the limit raised, Dependabot starts

item 12, but AUTO-03's acceptance rests on it. The endpoint and the pattern exist (`immutable-releases`).
**Fix:** Add an `automated-security-fixes` control (`{ "enabled": true }`, `PUT` bodiless, read `repos/{owner}/{repo}/automated-security-fixes`)
and a `dependabot.yml` assertion in `verify-workflows` or a small verifier: npm entry has `open-pull-requests-limit: 0`, no
`automerge`-like keys, ecosystem set equals {github-actions, npm}, no `registries`. Give it a `--self-test` with each fault planted.

## Info

### IN-01: Dependabot cannot collide with the train's PR lookups

Checked, no defect. Every lookup is by exact branch name (`openPrFor`: `p.head === head`; `gh pr list --head chore/esr-<tag>`,
`--head chore/node-v24.x`, merged lookup `--head chore/esr-<PIN>`) plus `isCrossRepository == false`. Dependabot branches are
`dependabot/github_actions/...` and `dependabot/npm_and_yarn/theia/...`, same-repo, so they appear in `open-prs.txt` and are ignored.
The open-PR list line format `^(\d+) (\S+)$` accepts them. The fixer's `claude-fix/` and Renovate's `chore/theia-` prefixes cannot be
matched by a Dependabot branch. `workflow_run` is held out, so a red Dependabot PR starts no fixer today; when the trigger is re-added,
the fixer guard (`actor != 'powerbrowser-bot[bot]'`) will not exclude `dependabot[bot]`, so a red Dependabot PR would start Claude on a
Dependabot branch. Add `dependabot[bot]` to that guard at that time.

### IN-02: repo-controls read logic is sound; two small edges

Verified: `alertsFromStatus` maps only `empty === true` (a 2xx with an empty body) and `status === 404`; `ghGet` sets `empty` only after
a successful exec whose output fails `JSON.parse` and trims to `''`, and `status` only from `(HTTP 404)` in the first stderr line. A 403,
a 500, non-JSON text, a spawn failure and a 404 on any control without `liveFrom` stay `ok: false`. The `empty`-on-other-control case has a
plant. A missing control cannot read green: a 404 maps to `enabled: false` against declared `true`, red. Edges: (a) a 404 caused by a
token that cannot see the repository is reported as "enabled is false live", not as an auth problem, so the owner gets the wrong
next step; (b) `compareDefaultSetup` accepts `declared.languages ?? []`, so a body edited to `languages: []` or with the key removed
compares vacuously (state and suite are still compared). Require a non-empty declared array.
